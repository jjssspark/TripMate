## ADR-1. Gemini 모델 이원화 + thinking 모드 비활성화

**맥락**
"로딩 30초 이내" 요구가 있었는데, Netlify Functions는 동기 호출 구조라 실행시간 상한이 빡빡하다. Gemini 2.5 Flash 계열은 thinking(내부 추론) 모드가 기본 켜져 있어, 이게 원인이 되어 502/504 타임아웃이 반복됐다.

**선택지**
1. thinking 모드를 유지하고 타임아웃 자체를 늘린다
2. thinking 모드를 끄고 응답 속도를 확보한다
3. 더 가벼운 모델로 완전히 교체한다

**결정**
`thinkingConfig: { thinkingBudget: 0 }`으로 thinking을 끄고, 주 모델(`gemini-2.5-flash`) 실패 시 보조 모델(`gemini-2.5-flash-lite`), 그마저 실패하면 주 모델로 마지막 재시도까지 3단계 폴백 체인을 구성했다.

**근거**
서버리스 함수의 실행시간 상한은 플랫폼 제약이라 늘릴 수 없었다. 응답을 JSON 스키마로 강제 출력하는 구조라 thinking 체인이 답변 품질에 주는 이득이 크지 않은 반면, 지연시간에는 직접적인 영향을 줬다.

**결과**
502/504는 해소됐다. 다만 이후 응답 시간이 17~25초 사이로 흔들리는 게 드러나 타임아웃 예산을 다시 손봐야 했다(그 뒷이야기는 트러블슈팅 문서 3번에 있다) — "thinking만 끄면 끝날 것"이라는 최초 예측은 절반만 맞았다.

## ADR-2. Supabase를 서버 경유 없이 브라우저에서 직접 호출

**맥락**
여행 일정 CRUD(저장·조회·삭제)는 로그인한 사용자별 데이터라 인증과 결합된 DB 접근이 필요했다. Gemini·Places처럼 비밀키가 필요한 외부 API와 달리, Supabase의 anon key는 애초에 클라이언트에 노출되는 것을 전제로 설계된 키이고, 대신 RLS(Row Level Security)로 접근을 통제하는 구조다.

**선택지**
1. 자체 REST API 서버(Express/Netlify Functions)를 하나 두고, 그 뒤에서만 Supabase를 호출한다
2. 브라우저에서 Supabase JS 클라이언트로 직접 CRUD하고, RLS 정책으로 소유권을 통제한다
3. 읽기는 직접 호출, 쓰기는 서버 경유로 나눈다

**결정**
2번. 브라우저가 Supabase를 직접 호출하고, `user_seq` 소유권 검사를 RLS 정책에 위임했다.

**근거**
자체 API 계층을 하나 더 두면 서버가 사실상 Supabase 요청을 그대로 전달하는 얇은 프록시가 되어 코드만 늘어난다. anon key + RLS 조합은 이 직접 호출 패턴을 전제로 설계된 것이라, 서버를 하나 더 두는 것보다 RLS 정책을 촘촘히 짜는 쪽이 더 정확한 방향이라고 판단했다. 반대로 Gemini·Places 키는 anon 공개를 전제하지 않으므로 그건 서버 경유로 남겨, 결과적으로 "DB는 직접, 외부 AI/지도 API는 서버 경유"인 비대칭 구조가 됐다.

**결과**
두 계층이 공존하는 구조가 실제로 다른 사고의 진단을 늦추는 부작용을 냈다 — Supabase가 일시정지됐을 때(트러블슈팅 문서 1번) "서버 로그가 비어 있다"는 신호가, 이 구조를 모르면 헷갈리는 단서였다. 이 결정이 나중에 다른 문제의 진단 난이도를 높였다는 것도 정직하게 남긴다. 그럼에도 RLS로 통제되는 한 직접 호출 자체는 보안상 허용 가능한 패턴이라 유지하기로 했다.

## ADR-3. 명소 추천은 정적 데이터로 고정하고, 사진만 Places API로 동적 조회

**맥락**
Must-Visit 추천과 AI 생성 실패 시 폴백 콘텐츠에 쓸 실제 장소명이 필요했다. Google Places API는 이미 장소 사진 조회용으로 서버에 연동돼 있었다.

**선택지**
1. 장소명도 Places Text Search로 매번 실시간 조회한다
2. 목적지별 정적 데이터셋(국내 100곳 × 각 3곳)을 코드에 직접 정의한다

**결정**
2번. 장소명 추천은 정적 데이터로, 사진만 Places Photo API로 동적 조회하는 하이브리드 구조를 택했다.

**근거**
Places Text Search는 목적지별로 "진짜 유명한 곳"을 보장하지 않고(리뷰 수·카테고리 랭킹이 프로젝트 의도와 다르게 나올 수 있음), 매 요청마다 과금과 지연이 추가된다. 정적 리스트는 "목록에 없는 목적지는 빈 배열을 반환해 추천 줄 자체를 숨긴다 — 그럴듯한 일반 문구로 채우면 추천의 신뢰가 깨진다"는 원칙을 코드에 명시할 만큼, 어설픈 실시간 데이터보다 신뢰를 지키는 쪽을 택했다.

**결과**
AI 생성이 실패해 폴백이 나갈 때도(트러블슈팅 문서 3번 사고) 이 정적 데이터가 그대로 재사용되어 실제 명소명이 노출됐다 — 애초 의도하지 않았던 곳에서 이 결정이 유용하게 재활용된 사례. 다만 목적지가 100곳으로 국한돼 목록 밖 지명은 추천이 아예 뜨지 않는 트레이드오프가 남는다 — 의도된 제한으로 문서화했다.

## ADR-4. 자동완성 초성 검색을 라이브러리 없이 직접 구현

**맥락**
목적지 자동완성에서 완전일치 후보가 사라지는 버그를 고치면서(트러블슈팅 문서 5번), 초성 검색 기능까지 함께 요구받았다.

**선택지**
1. `hangul-js`, `es-hangul` 같은 기존 한글 처리 라이브러리를 붙인다
2. 유니코드 완성형 음절 코드 계산(U+AC00 기반)으로 직접 구현한다

**결정**
2번. 필요한 기능을 순수 함수로 직접 짰다.

**근거**
필요한 건 "초성 추출 + startsWith/includes 매칭" 하나뿐이라 라이브러리 전체를 번들에 넣는 게 과했다(랜딩 페이지 JS 번들 예산 150kb 제한도 고려 대상이었다). 완성형 한글 음절의 초성 계산 공식은 짧고 고정적이라 직접 구현 비용이 낮았다.

**결과**
번들 증가 없이 기능을 구현했다. 다만 완성형 음절만 처리하기 때문에 IME 조합 중간 상태(자모가 아직 합쳐지지 않은 입력)는 대상 밖이라는 한계가 남았다 — 실사용에서는 문제가 되지 않아 받아들이기로 했고, 이 한계를 알면서도 남겨둔 이유까지 문서에 적었다.

## ADR-5. 소셜 로그인 제거, 이메일/비밀번호 인증으로 단일화

**맥락**
로그인 화면에 Google/Kakao/Naver 소셜 버튼이 있었지만, 아이콘이 외부 호스팅 이미지(`lh3.googleusercontent.com`)를 그대로 참조하고 있어 흰 배경만 남은 스크린샷처럼 보였다. 게다가 실제로 연동된 provider가 하나도 없었다.

**선택지**
1. 소셜 로그인 provider 3개를 실제로 구현해 완성한다
2. 미완성 상태로 두고 "준비 중" 표시만 한다
3. 아예 제거한다

**결정**
3번. 이메일/비밀번호 단일 경로로 단순화했다.

**근거**
MVP 범위에서 provider 3개를 전부 붙이는 건 일정 대비 과했고, 동작하지 않는 버튼을 화면에 남겨두는 쪽이 오히려 신뢰를 더 깎는다고 판단했다. OAuth를 전제로 쓰인 주석은 갱신했지만, 회원가입 도중 `users` 행 insert가 실패한 계정을 위한 폴백 생성 로직은 그대로 유지했다 — 이건 소셜 로그인 여부와 무관하게 필요한 안전장치였기 때문이다.

**결과**
코드 76줄이 삭제됐고, 호출자가 사라진 `handleSocialClick` 콜백을 제거하는 과정에서 그 안에 있던 `alert()` 1곳도 부수적으로 함께 사라졌다(트러블슈팅 문서 4번과 연결되는 지점). "왜 제거했는지"를 커밋 메시지에 원인(스크린샷에 흰 배경)까지 구체적으로 남겨둬서, 나중에 재도입을 검토할 때도 참고할 근거가 남아 있다.
