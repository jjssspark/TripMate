## 1. "Failed to fetch" — 사실은 서버가 아니라 DNS가 죽어 있었다

**해당 기준**: 처음 가설이 틀림 · 에러 메시지와 원인 불일치 · 환경/인프라 문제

**증상**
로컬 dev 서버는 정상 기동했는데, 브라우저에서 로그인·일정 저장 등 Supabase가 관여하는 모든 동작이 실패했다. 화면엔 `Failed to fetch`만 떴고, dev 서버 로그에는 요청 흔적조차 없었다.

**원인**
Supabase 무료 플랜 프로젝트가 비활성 기간이 쌓여 자동 일시정지되면서 프로젝트 도메인이 DNS에서 사라졌다. 브라우저는 DNS 해석 단계에서 죽기 때문에 HTTP 상태 코드조차 받지 못했고, 이 앱은 Supabase를 브라우저에서 직접 호출하는 구조라 로컬 Express 서버 로그에는 애초에 남을 이유가 없었다.

**틀렸던 가설들**
1. dev 서버 로그를 뒤짐 → 단서 0건 (서버를 안 거치는 구조였다)
2. 이번 세션에 건드린 코드 커밋을 의심 → 무관 판명
3. `curl`로 첫 확인 시 `HTTP=000` → 이때 자신의 실행 환경 네트워크 자체를 먼저 배제했어야 했는데 그러지 않아 진단이 한 바퀴 더 돌았다

**해결**
Supabase 대시보드에서 프로젝트 Resume. 다만 즉시 복구되지 않고 인증(GoTrue) → REST(PostgREST) 순으로 약 2분에 걸쳐 단계적으로 올라온다는 걸 실측으로 확인했다. 복구 중간에는 `PGRST002`/`404`가 떠서 "테이블이 삭제됐다"로 오인하기 쉬운데, 실제로는 기동 중 상태였다.

**배운 점**
"Failed to fetch"는 애플리케이션 에러가 아니라 네트워크 계층에서 죽었다는 신호다. `nslookup` 한 번이 서버 코드를 뒤지는 30분을 아낀다. 그리고 어느 계층이 호출하는지 알아야 어느 로그를 볼지가 정해진다 — 이 앱은 서버를 경유하지 않는 구조였는데 그걸 모르면 계속 헤맨다. 진단 순서로는, 상대가 죽었는지 내가 못 나가는지부터 먼저 구분해야 한다.

## 2. 빌드는 성공했는데 아이콘이 하나도 없다 — 조용히 실패하는 설정

**해당 기준**: 에러 메시지와 원인 불일치 (에러 자체가 없었다)

**증상**
`npm run build`는 경고 없이 성공했다. 그런데 배포된 앱에 PWA 설치 아이콘과 파비콘이 나오지 않았다. `dist/`를 열어보니 이미지 파일이 단 하나도 없었다.

**원인**
직전 리팩터링 커밋에서 `static/` 폴더를 `public/static/`으로 옮기면서, `vite.config.ts`의 `publicDir: 'static'` 설정은 그대로 뒀다. Vite는 `publicDir`가 가리키는 경로가 존재하지 않으면 **에러도 경고도 없이 조용히 건너뛴다.** "빌드 성공"이라는 신호가 아무것도 보장해주지 못하는 상태였던 것.

**해결**
`publicDir`를 실제 폴더로 교정하고, 자산을 매니페스트가 참조하는 경로 구조에 맞춰 평탄화했다. `netlify.toml`에 남아있던 같은 종류의 죽은 리다이렉트 참조도 함께 제거했다.

**배운 점**
"빌드 성공"과 "산출물이 올바르다"는 다른 말이다. 경로가 없으면 조용히 넘어가는 설정은 실패를 신호로 바꿔주지 않기 때문에, 파일을 옮기는 리팩터링에서는 *그 경로를 문자열로 알고 있던 곳*을 기준으로 검토해야 한다 — "옮긴 파일"이 아니라. 재발 방지로 빌드 후 산출물 존재를 검사하는 스모크 체크가 필요하다는 결론까지 남겼다.

## 3. AI 응답이 늦으면 조용히 가짜 일정이 나갔다 — 타임아웃 예산을 잘못 나눈 대가

**해당 기준**: 간헐적 재현 · 우회 해결 · 처음 가설이 틀림

**증상**
AI가 만든 일정의 장소 이름이 전부 "제주도 인기 명소 3" 같은 뭉뚱그린 일반명사로 나왔다. 사용자 입장에선 "AI 추천 품질이 나쁘다"로만 보였다.

**원인**
"로딩 30초 이내" 요구에 맞춰 27초 예산을 도입하며 배분을 잘못했다. 주 모델에 18초만 주고 실패 시 재시도에 5.5초만 남겼는데, 재시도는 빠른 실패(503 등)에만 의미가 있어 타임아웃으로 실패하면 남은 예산으로는 아무것도 못 한다. 결국 예외가 나서 기존 폴백(목업 일정)이 반환됐는데, **그 폴백이 정상 응답과 구분되지 않고 그대로 화면에 노출**되고 있었다. Gemini 응답 시간이 17~25초 사이로 흔들려 임계값을 간헐적으로 넘나든 것도 확인의 실마리였다.

**틀렸던 가설**
처음엔 "프롬프트가 부실해서 품질이 낮다"고 보고 프롬프트 규칙을 강화했다. 증상은 그대로였다 — Gemini가 애초에 호출되지 못하고 있었으니 프롬프트를 아무리 고쳐도 닿지 않는 지점이었다.

**해결**
주 모델에 예산 대부분을 몰아주고, 폴백이 나갈 땐 `isFallback: true`를 응답에 실어 화면에 드러내도록 바꿨다. 폴백 데이터 자체도 프론트가 쓰던 실제 명소 목록을 서버가 그대로 재사용하도록 통일했다. 근본 해결(스트리밍/비동기 큐)은 하지 않았고, 지금은 예산 재조정으로 버티는 상태임을 그대로 남겼다.

**배운 점**
타임아웃을 넣을 때는 "얼마 안에 끝낼까"만큼 "그 예산을 어떻게 나눌까"가 중요하다. 그리고 조용한 폴백은 버그를 품질 문제로 위장한다 — 폴백은 반드시 폴백임이 드러나야 원인 조사가 엉뚱한 곳에서 시작되지 않는다.

## 4. 브라우저 자동화가 이유 없이 멈춘다 — `alert()`가 렌더러를 블로킹하고 있었다

**해당 기준**: 에러 메시지와 원인 불일치 · 정직한 재조사(1차 보고가 불완전했던 것)

**증상**
브라우저 자동화로 폼 검증을 확인하던 중 클릭 이후 탭이 완전히 응답 불능이 됐다. 클릭·스크린샷·스크립트 주입이 전부 타임아웃 났고 서버 로그에는 요청이 하나도 안 찍혔다.

**원인**
검증 실패를 브라우저 모달 `alert()`로 띄우고 있었다. `alert()`는 JS 실행과 렌더러를 동기적으로 블로킹하므로 자동화가 보내는 모든 후속 명령이 큐에 쌓인 채 타임아웃됐다 — "프리즈"가 아니라 "모달 대기 상태"였던 것.

**해결**
이미 존재하던 Toast 컴포넌트로 교체했다(새 컴포넌트를 만들지 않았다). 다만 처음엔 "3곳"이라고 보고했다가 실제로는 `src/` 전체에 10곳이 있었다 — grep 범위를 파일 2개로 좁혔던 게 원인이었다. 이후 컴포넌트 단위가 아니라 디렉터리 전체로 다시 훑었다. 파괴적 동작을 확인하는 `confirm()` 2곳은 토스트로 바꾸지 않고 남겨뒀다 — 안전장치이기 때문에, 대체하려면 별도의 확인 모달이 필요하다는 걸 명시했다.

**배운 점**
`alert()`/`confirm()`은 UX 이전에 테스트 가능성(testability) 문제다. 렌더러를 블로킹하기 때문에 자동화가 그 지점에서 죽는데, 죽는 방식이 "타임아웃"이라 원인이 프론트엔드에 있다는 힌트조차 안 준다. 자동화가 이유 없이 멈추면 네트워크·서버보다 모달 API부터 grep하는 게 빠르다. 그리고 전수 조사는 처음부터 범위를 좁히면 안 된다는 것도 이번에 확인했다.

## 5. 자동완성이 "정확히 일치하는 순간" 후보를 감췄다

**해당 기준**: 논리 버그 진단 (필터 조건 vs 데이터 존재 여부를 구분하는 사례)

**증상**
목적지 입력란에 "도쿄"를 끝까지 입력하면 목록에 분명 있는데도 자동완성에서 사라졌다. 한 글자씩 지울 때는 보였다 — "도"에서는 보이고 "도쿄"가 되는 순간 사라지는 패턴이었다.

**원인**
필터 조건에 `d !== destination.trim()`, 즉 입력값과 완전히 같은 후보를 제외하는 절이 있었다. "이미 입력한 것과 똑같은 걸 또 제안하지 말자"는 의도였겠지만, 정작 사용자가 지명을 정확히 아는 가장 흔한 경우에 목록이 통째로 비어버리는 결과를 낳았다.

**해결**
검색 로직을 컴포넌트 밖 순수 함수로 분리하고, 완전일치를 배제하지 않고 최상위로 올리는 랭킹 방식(완전일치 → 접두 → 포함 → 초성)으로 바꿨다. 겸사겸사 초성 검색도 추가했다.

**배운 점**
"중복 제거"처럼 보이는 방어 조건이 정상 경로를 막는 경우가 있다. 필터에 배제 조건을 넣을 때는 "이 조건이 참이 되는 상황이 정말 예외적인가"를 먼저 따져야 한다. 그리고 "목록에 있는데 안 나온다"는 데이터가 아니라 조회 조건을 의심해야 한다는 신호다.
