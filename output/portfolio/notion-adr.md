# 기술 의사결정 (ADR)

이 프로젝트에서 내린 기술 결정과 그 대가를 기록한다. 결정 자체보다 무엇을 포기했는지에 무게를 뒀다.

| --- | --- | --- | --- | --- |
| 1 | Gemini thinking 끄고 3단계 폴백 체인 | 502/504 해소 | 응답 시간이 17~25초로 흔들림 | 부분 대체 |
| 2 | Supabase를 브라우저에서 직접 호출 | 얇은 프록시 계층을 안 만듦 | 두 계층 공존으로 진단 난이도 상승 | 유효 |
| 3 | 명소는 정적 데이터, 사진만 API | 추천 신뢰도 확보 | 목록 밖 지명은 추천이 안 뜸 | 부분 대체 |
| 4 | 초성 검색을 라이브러리 없이 직접 구현 | 번들 증가 0 | IME 조합 중간 상태는 처리 못 함 | 유효 |

| 6 | 무료 한도 안에서 호출량 축소 | 하루 처리량 2배 | 하루 10건 상한 | 유효 |

## ADR-1. Gemini 모델 이원화 + thinking 모드 비활성화

> "thinking만 끄면 끝날 것"이라는 예측은 절반만 맞았다.

### 맥락

"로딩 30초 이내" 요구가 있었는데 Netlify Functions는 동기 호출 구조라 실행시간 상한이 빡빡하다. 그런데 Gemini 2.5 Flash 계열은 thinking(내부 추론) 모드가 기본으로 켜져 있고, 이것 때문에 502/504 타임아웃이 반복됐다.

### 선택지

| | 안 | 판단 |
| --- | --- | --- |
| 1 | thinking을 유지하고 타임아웃 자체를 늘린다 | 기각 |
| 2 | thinking을 끄고 응답 속도를 확보한다 | 채택 |
| 3 | 더 가벼운 모델로 완전히 교체한다 | 기각 |

### 결정

`thinkingConfig: { thinkingBudget: 0 }`으로 thinking을 끄고, 폴백 체인을 3단계로 구성했다.

주 모델(`gemini-2.5-flash`) → 실패 시 보조 모델(`gemini-2.5-flash-lite`) → 그마저 실패하면 주 모델로 마지막 재시도.

### 근거

서버리스 함수의 실행시간 상한은 플랫폼 제약이라 늘릴 수 없었다. 1번이 애초에 불가능한 선택지였다는 뜻이다.

응답을 JSON 스키마로 강제 출력하는 구조라 thinking 체인이 답변 품질에 주는 이득은 크지 않았다. 반면 지연시간에는 직접적으로 영향을 줬다.

### 결과

502/504는 해소됐다. 다만 그 뒤에 응답 시간이 17~25초 사이로 흔들리는 게 드러나 타임아웃 예산을 다시 손봐야 했다. 뒷이야기는 트러블슈팅 문서 3번에 있다.

### 후속 (2026-08-16)

폴백 체인은 파이프라인 교체로 제거됐다. 현재는 후보 추출과 설명 모두 `gemini-2.5-flash` 단일이고, `flash-lite`는 코드에 없다.

모델을 갈아타는 대신 단계별 타임아웃과 실패 종류 분리(422/429)로 대체했다. 모델을 바꿔도 느린 건 느린 거라, 대체 모델보다 "언제 포기할지"를 정하는 쪽이 실효가 있었다.

thinking 비활성화는 그대로 유지 중이다. 이 결정은 살아남았다.

`flash-lite`는 폐기가 아니라 보류다. 무료 한도가 모델별로 잡히므로 호출량이 한도를 넘으면 버킷을 나누는 카드로 쓸 수 있다. ADR-6 참조.

## ADR-2. Supabase를 서버 경유 없이 브라우저에서 직접 호출

> 이 결정이 나중에 다른 문제의 진단 난이도를 높였다는 것도 남긴다.

### 맥락

여행 일정 CRUD는 로그인한 사용자별 데이터라 인증과 결합된 DB 접근이 필요했다.

여기서 키의 성격이 갈린다. Gemini나 Places 키는 비밀키다. 반면 Supabase의 anon key는 애초에 클라이언트 노출을 전제로 설계된 키이고, 대신 RLS(Row Level Security)로 접근을 통제하는 구조다.

### 선택지

| | 안 | 판단 |
| --- | --- | --- |
| 1 | 자체 REST API 서버를 두고 그 뒤에서만 Supabase 호출 | 기각 |
| 2 | 브라우저에서 직접 CRUD하고 RLS로 소유권 통제 | 채택 |
| 3 | 읽기는 직접, 쓰기는 서버 경유로 분리 | 기각 |

### 결정

브라우저가 Supabase를 직접 호출하고, `user_seq` 소유권 검사를 RLS 정책에 위임했다.

### 근거

자체 API 계층을 하나 더 두면 서버가 Supabase 요청을 그대로 전달하는 얇은 프록시가 되어 코드만 늘어난다. anon key + RLS 조합은 이 직접 호출 패턴을 전제로 설계된 것이라, 서버를 하나 더 두는 것보다 RLS 정책을 촘촘히 짜는 쪽이 더 정확한 방향이라고 봤다.

반대로 Gemini와 Places 키는 공개를 전제하지 않으므로 서버 경유로 남겼다. 결과적으로 비대칭 구조가 됐다.

- DB → 브라우저에서 직접
- 외부 AI·지도 API → 서버 경유

### 결과

두 계층이 공존하는 구조가 실제로 다른 사고의 진단을 늦췄다. Supabase가 일시정지됐을 때(트러블슈팅 문서 1번) "서버 로그가 비어 있다"는 신호가, 이 구조를 모르면 헷갈리는 단서였다.

그럼에도 RLS로 통제되는 한 직접 호출 자체는 보안상 허용 가능한 패턴이라 유지하기로 했다.

## ADR-3. 명소 추천은 정적 데이터로 고정하고, 사진만 Places API로 동적 조회

> 어설픈 실시간 데이터보다 신뢰를 지키는 쪽을 택했다.

### 맥락

Must-Visit 추천과 AI 생성 실패 시 폴백 콘텐츠에 쓸 실제 장소명이 필요했다. Google Places API는 이미 장소 사진 조회용으로 서버에 연동돼 있었다.

### 선택지

| | 안 | 판단 |
| --- | --- | --- |
| 1 | 장소명도 Places Text Search로 매번 실시간 조회 | 기각 |
| 2 | 목적지별 정적 데이터셋(국내 100곳 × 각 3곳)을 코드에 정의 | 채택 |

### 결정

장소명 추천은 정적 데이터로, 사진만 Places Photo API로 동적 조회하는 하이브리드 구조를 택했다.

### 근거

Places Text Search는 목적지별로 "진짜 유명한 곳"을 보장하지 않는다. 리뷰 수나 카테고리 랭킹이 프로젝트 의도와 다르게 나올 수 있고, 매 요청마다 과금과 지연이 붙는다.

그래서 원칙을 코드에 명시했다. 목록에 없는 목적지는 빈 배열을 반환해 추천 줄 자체를 숨긴다. 그럴듯한 일반 문구로 채우면 추천의 신뢰가 깨지기 때문이다.

### 결과

의도하지 않은 곳에서 이 결정이 재활용됐다. AI 생성이 실패해 폴백이 나갈 때도(트러블슈팅 문서 3번) 이 정적 데이터가 그대로 쓰여 실제 명소명이 노출됐다.

남은 트레이드오프는 목적지가 국내 100곳으로 국한된다는 것이다. 목록 밖 지명은 추천이 아예 뜨지 않는다. 의도된 제한으로 문서화했다.

### 후속 (2026-08-17)

절반이 뒤집혔다.

정적 데이터는 그대로 유지 중이다. Must-Visit 추천에 계속 쓰인다.

사진 쪽은 포기했다. Google Maps Platform이 무료 사용량 안에서도 결제 계정 등록을 요구하는데, 이 프로젝트는 카드 등록 없이 운영하기로 했다. 프록시 엔드포인트(`/api/place-photo`)와 조회 코드는 남겨두고 키만 두지 않는다. 키가 없으면 카테고리별 목업 이미지로 내려가는 경로가 원래 설계돼 있었다.

폴백에서의 재활용도 무효가 됐다. 폴백 자체를 제거했기 때문이다(ADR-6, 트러블슈팅 3번).

남은 것은 "실시간 조회보다 정적 목록을 신뢰한다"는 원칙 하나다. 그 원칙은 지금도 유효하다.

## ADR-4. 자동완성 초성 검색을 라이브러리 없이 직접 구현

> 필요한 건 함수 하나였는데 라이브러리 전체를 번들에 넣을 이유가 없었다.

### 맥락

목적지 자동완성에서 완전일치 후보가 사라지는 버그를 고치면서(트러블슈팅 문서 5번), 초성 검색 기능까지 함께 요구받았다.

### 선택지

| | 안 | 판단 |
| --- | --- | --- |
| 1 | `hangul-js`, `es-hangul` 같은 기존 라이브러리를 붙인다 | 기각 |
| 2 | 유니코드 완성형 음절 코드 계산(U+AC00 기반)으로 직접 구현 | 채택 |

### 결정

필요한 기능을 순수 함수로 직접 짰다.

### 근거

필요한 건 "초성 추출 + startsWith/includes 매칭" 하나뿐이었다. 랜딩 페이지 JS 번들 예산 150kb 제한도 고려 대상이었다.

완성형 한글 음절의 초성 계산 공식은 짧고 고정적이라 직접 구현 비용이 낮았다.

### 결과

번들 증가 없이 기능을 구현했다.

다만 완성형 음절만 처리하기 때문에 IME 조합 중간 상태(자모가 아직 합쳐지지 않은 입력)는 대상 밖이다. 실사용에서 문제가 되지 않아 받아들이기로 했고, 이 한계를 알면서도 남겨둔 이유까지 문서에 적었다.

## ADR-5. 소셜 로그인 제거, 이메일/비밀번호 인증으로 단일화

> 동작하지 않는 버튼을 남겨두는 쪽이 신뢰를 더 깎는다.

### 맥락

로그인 화면에 Google/Kakao/Naver 소셜 버튼이 있었는데 상태가 두 겹으로 나빴다.

- 아이콘이 외부 호스팅 이미지를 그대로 참조해 흰 배경만 남은 스크린샷처럼 보였다
- 애초에 실제로 연동된 provider가 하나도 없었다

### 선택지

| | 안 | 판단 |
| --- | --- | --- |
| 1 | provider 3개를 실제로 구현해 완성한다 | 기각 |
| 2 | 미완성 상태로 두고 "준비 중" 표시만 한다 | 기각 |
| 3 | 아예 제거한다 | 채택 |

### 결정

이메일/비밀번호 단일 경로로 단순화했다.

### 근거

MVP 범위에서 provider 3개를 전부 붙이는 건 일정 대비 과했다.

OAuth를 전제로 쓰인 주석은 갱신했지만, 회원가입 도중 `users` 행 insert가 실패한 계정을 위한 폴백 생성 로직은 그대로 뒀다. 이건 소셜 로그인 여부와 무관하게 필요한 안전장치였다.

### 결과

코드 76줄이 삭제됐다. 호출자가 사라진 `handleSocialClick` 콜백을 지우는 과정에서 그 안에 있던 `alert()` 1곳도 부수적으로 함께 사라졌다. 트러블슈팅 문서 4번과 연결되는 지점이다.

커밋 메시지에 "왜 제거했는지"를 원인(스크린샷에 흰 배경)까지 구체적으로 남겨둬서, 나중에 재도입을 검토할 때 참고할 근거가 있다.

## ADR-6. 무료 티어를 유지하되 한도를 늘리지 않고 호출량을 줄인다

> 한도가 부족하면 한도를 사는 게 아니라 소비를 줄이는 게 먼저다.

### 맥락

Gemini 무료 티어는 모델·프로젝트당 하루 20회다. 그런데 파이프라인 1회가 `후보 추출 1회 + 일수만큼의 설명 호출`을 써서, 3일 일정이면 4회가 나갔다. 일정 다섯 건이면 그날 한도가 바닥나고 일정 생성이 통째로 실패했다(트러블슈팅 문서 6번).

### 선택지

| | 안 | 판단 |
| --- | --- | --- |
| 1 | 유료 티어로 전환해 한도를 푼다 | 기각 |
| 2 | 설명 호출을 여행 전체 1회 배치로 합친다 | 채택 |
| 3 | 후보 추출과 설명을 서로 다른 모델에 태워 버킷을 나눈다 | 보류 |
| 4 | 응답의 `retryDelay`만큼 기다렸다 재시도한다 | 기각 |

### 결정

설명 생성을 일차별 N회에서 여행 전체 1회 배치로 합쳤다. 일정 1건당 호출이 4회에서 2회가 됐고, 하루 처리량이 5건에서 10건으로 늘었다.

함께 두 가지를 붙였다.

- 429를 `AI_QUOTA_EXCEEDED`로 분리해 재시도 시각까지 안내. 500에 섞으면 "조건을 바꿔 보라"는 틀린 안내가 나간다
- 쿼터 오류는 재시도 대상에서 제외. 429는 다시 불러도 429고, 남은 한도만 더 깎는다

### 근거

1번은 무료 운영 방침과 충돌한다.

4번은 무효다. 걸린 것이 분당 한도가 아니라 일 한도라 기다려도 풀리지 않는다. 응답만 20초 느려진다.

3번은 실제로 효과가 있다. 쿼터가 모델별로 잡히므로 설명을 `flash-lite`로 옮기면 버킷이 분리돼 하루 20건이 된다. 다만 목표 처리량이 10건이라 지금은 불필요한 복잡도라고 봤다. 모델 문자열 한 줄이면 언제든 켤 수 있어 보류로 남긴다.

배치 호출이 품질을 해치지 않는다는 것도 확인이 필요했다. 검증을 일차별로 유지해서, 어긋난 일차만 폴백으로 내리고 나머지는 살리도록 했다. 폴백 세밀도를 잃지 않았다.

### 결과

| 지표 | 이전 | 이후 |
| --- | --- | --- |
| 일정 1건당 Gemini 호출 | 4회 (3일 기준) | 2회 |
| 하루 처리량 | 약 5건 | 약 10건 |
| 한도 소진 시 응답 | 500, 25초 예산 소모 | 429, 0.55초 |

남은 대가는 두 가지다.

하루 10건 상한은 그대로 남는다. 데모나 심사 시점에 소진돼 있을 수 있다.

배치 프롬프트라 일수가 길면 응답이 길어진다. 7일 이상에서 응답이 잘리면 일차별 검증이 잡아 폴백으로 내려가므로 일정 자체는 나오지만 설명 품질이 떨어진다. 실측 후 필요하면 쪼갤 것으로 남겼다.

## 여섯 건에서 반복된 것

플랫폼 제약을 인정하고 그 위에서 최적화한 결정이 많다. ADR-1은 서버리스 실행시간 상한을 늘릴 수 없다는 데서 출발했고, ADR-2는 anon key가 노출을 전제로 설계됐다는 성격을 받아들인 결과다. ADR-6은 무료 한도를 상수로 두고 소비 쪽을 움직였다. 바꿀 수 없는 걸 먼저 확정하고 나면 선택지가 오히려 줄어든다.

그리고 여섯 건 모두 결과 항목에 남은 대가를 적었다. ADR-2는 자기 결정이 나중에 진단을 어렵게 했다는 것까지 썼다. 결정을 정당화하는 문서가 아니라 다음 사람이 판단을 뒤집을 수 있게 만드는 문서를 목표로 했다.

실제로 두 건이 뒤집혔다. ADR-1의 폴백 체인은 제거됐고 ADR-3의 사진 조회는 포기했다. 뒤집힌 결정을 지우지 않고 후속으로 남긴 이유도 같다. 왜 그렇게 정했고 왜 바꿨는지가 함께 있어야 다음 판단이 빨라진다.
