# 회고

혼자 만든 프로젝트라 결정을 검토해 줄 사람이 없었다. 대신 판단할 때마다 이유를 문서에 남겼고, 한 달 뒤 그 문서를 근거로 스스로 뒤집었다. 이 회고는 그 뒤집힌 기록이다.

---

## 결과부터

| 항목 | 상태 |
|---|---|
| 일정 생성 | 6단계 검증 파이프라인. 실재하지 않는 장소를 걸러낸다 |
| 실패 처리 | 실패를 숨기지 않고 상태 코드로 드러낸다 (422 / 429 / 500) |
| 무료 한도 | 일정 1건당 AI 호출 2회. 하루 10건 생성 가능 |
| 테스트 | 파이프라인 핵심 로직 단위 테스트 통과 |
| 남은 것 | 배포 환경변수 누락으로 운영 데모 복구 대기 |

## 지금도 유효한 판단

### 폴백을 없앤 것

AI가 실패하면 정적 데이터로 그럴듯한 일정을 만들어 200으로 돌려주고 있었다. 화면에는 정상처럼 보였다.

이걸 없앴다. 실재하지 않는 일정을 보여주는 것보다 실패를 드러내는 게 낫다고 판단했다. 사용자가 "왜 이 장소가 여기 있지"라고 의심하는 상태를, 서비스가 만들어서는 안 된다고 봤다.

### 판단을 코드가 아니라 문서에 남긴 것

ADR 6건, 트러블슈팅 6건을 남겼다. 덕분에 한 달 뒤 "왜 이렇게 했더라"를 다시 추측하지 않았고, 뒤집을 때도 무엇을 뒤집는지 정확히 알았다.

실제로 ADR 두 건이 이번에 뒤집혔다. 지우지 않고 후속 항목으로 남겨뒀다.

### 장소 존재 검증을 외부 API로 넘긴 것

AI가 추천한 장소를 카카오 로컬 API로 대조한다. AI에게 "실재하는 곳만 말해달라"고 프롬프트로 부탁하는 방식은 검증이 불가능하다. 검증 가능한 지점으로 옮긴 판단이 맞았다.

## 다시 만든다면

### 1. AI 호출을 처음부터 비동기로

지금은 동기 호출 구조를 유지한 채 타임아웃 예산을 재분배해서 버티고 있다.

이 한 가지 제약 때문에 네 번을 고쳤다. 응답 시간, 코드 중복, 예산 배분, 무료 한도. 매번 다른 증상처럼 보였지만 뿌리는 같았다. 사용자 요청 하나가 AI 응답 하나에 통째로 묶여 있다는 것.

스트리밍이나 작업 큐로 시작했다면 이 반복이 없었다.

### 2. Supabase 테이블을 하나로

`users`와 `profiles`가 나뉘어 있는데, 왜 나뉘었는지 코드만으로는 설명이 안 된다. `profiles.eamil`처럼 컬럼명이 오타인 채로 남아 있기도 하다.

초기 스캐폴딩이 만든 테이블을 그대로 확장한 결과로 보인다. 스키마 문서를 쓰다가 알았다.

### 3. 실패 경로를 기능만큼 설계할 것

성공 경로는 처음부터 설계했지만, 실패 경로는 사고가 날 때마다 붙였다. 폴백, 타임아웃, 쿼터 소진 전부 그랬다.

그래서 폴백이 사고를 숨기는 역할을 하게 됐다. 실패했을 때 무엇을 보여줄지를 기능 설계 시점에 같이 정했어야 했다.

## 알면서 남겨둔 것

왜 아직 안 고쳤는지를 기준으로 묶었다.

### 설계를 바꿔야 해서 미룬 것

타임아웃 예산 재조정은 근본 해결이 아니라 버티기다. Gemini 응답이 17~25초로 흔들리는 한, 프롬프트가 조금만 길어져도 다시 임계값을 넘는다. 근본 해결은 설계 변경 폭이 커서 의도적으로 미뤘다.

### 감시만 걸어둔 것

`any` 타입이 39곳 남아 있다. Gemini 응답과 Supabase 반환값의 타입 경계에 몰려 있고, 응답 스키마 타입을 정의하면 대부분 없앨 수 있다. `@typescript-eslint/no-explicit-any`를 warn으로 켜서 lint 출력에 계속 노출시키는 중이다.

JS 번들이 gzip 209kB다. 예산 안이지만 Leaflet과 motion을 동적 import로 분리하지 않은 상태라 증가 추세가 남아 있다.

### 비용을 저울질하다 남긴 것

`users` / `profiles` 중복과 `eamil` 오타 컬럼. 둘 다 고칠 수 있다는 걸 알지만 실사용 데이터가 쌓여 있어 마이그레이션 비용을 저울질하는 중이다.

### 알고 받아들인 것

초성 검색이 완성형 음절만 처리한다. IME 조합 중간 상태는 대상 밖이다. 실사용에서 문제가 되지 않아 받아들였다.

## 가장 오래 붙잡은 문제

> 겉보기엔 서로 다른 사고 네 건이지만, 실은 같은 뿌리였다.

| 시점 | 증상 | 그때의 판단 |
|---|---|---|
| 7월 13일 | thinking 모드가 켜져 있어 502/504 타임아웃 | thinking을 끄면 해결된다고 봤다 |
| 직후 | 로컬 서버에는 같은 수정이 빠져 로컬만 타임아웃 | 코드 중복이 원인이라는 걸 이때 알았다 |
| 8월 2일 | thinking을 꺼도 17~25초로 흔들림. 예산 배분을 잘못해 목업 일정이 몰래 나감 | 처음엔 프롬프트 품질 문제로 잘못 짚었다 |
| 8월 16일 | 무료 한도 20회 소진. 일정 생성이 통째로 500 | 여기서야 호출 수 자체가 문제라는 걸 봤다 |

한 달 반 동안 같은 문제의 다른 얼굴을 네 번 만났다.

### 왜 네 번이나 걸렸나

매번 눈앞의 증상만 잡고 넘어갔기 때문이다. 모델 설정을 고치고, 코드 중복을 고치고, 예산 배분을 고쳤다. 셋 다 맞는 수정이었지만 전부 같은 층위의 대증요법이었다.

네 번째에 와서야 위층을 봤다. 일정 하나에 AI 호출이 1 + N회 나가고 있었다. 3박이면 4회. 하루 한도가 20회니 5건이면 끝난다.

호출을 묶어서 2회로 줄였다. 하루 10건이 됐고, 한도를 넘으면 25초를 태우지 않고 0.55초 만에 429를 돌려준다.

### 배운 것

호출 횟수는 성능 지표가 아니라 제약 조건이다. 무료 티어에서는 "얼마나 빠른가"보다 "몇 번 부르는가"가 서비스 수명을 정한다. 이걸 처음부터 예산으로 잡았어야 했다.

그리고 조용한 실패에 대한 답이 바뀌었다. 8월 2일에는 "폴백을 쓰되 플래그로 알리자"였는데, 8월 16일에는 "폴백 자체를 없애자"가 됐다. 플래그는 결국 개발자가 보는 것이고, 사용자는 화면에 뜬 일정을 믿는다.
