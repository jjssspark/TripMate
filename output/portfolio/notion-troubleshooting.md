## 1. `Failed to fetch` — 서버가 아니라 DNS가 죽어 있었다

> 서버 코드를 30분 뒤졌는데 `nslookup` 한 번이면 끝날 문제였다.

### 증상

로컬 dev 서버는 멀쩡히 떴다. 그런데 로그인이든 일정 저장이든 Supabase가 끼는 동작은 전부 실패했다. 화면에는 `Failed to fetch`만 뜨고, dev 서버 로그에는 요청이 들어온 흔적조차 없었다.

### 원인

Supabase 무료 플랜 프로젝트가 비활성 누적으로 자동 일시정지됐고, 프로젝트 도메인이 DNS에서 사라졌다. 브라우저가 DNS 해석 단계에서 죽으니 HTTP 상태 코드조차 못 받는다.

서버 로그가 텅 비어 있던 것도 당연했다. 이 앱은 브라우저가 Supabase를 직접 호출하는 구조라 애초에 서버를 거치지 않는다.

### 틀렸던 가설

| 시도 | 결과 |
| --- | --- |
| dev 서버 로그부터 확인 | 단서 0건. 서버를 안 거치는 구조 |
| 이번 세션 커밋 의심 | 무관 |
| `curl`로 확인 → `HTTP=000` | 이 시점에 내 네트워크부터 배제했어야 했는데 안 해서 한 바퀴 더 돌았다 |

### 해결

대시보드에서 프로젝트를 Resume했다. 바로 복구되진 않는다. 인증(GoTrue) → REST(PostgREST) 순으로 2분쯤 걸려 단계적으로 올라왔다. 중간에 `PGRST002`, `404`가 떠서 테이블이 삭제된 줄 알았는데 그냥 기동 중이었다.

### 배운 점

`Failed to fetch`는 애플리케이션 에러가 아니라 네트워크 계층에서 죽었다는 신호다.

그리고 어느 계층이 호출하는지를 알아야 어느 로그를 볼지가 정해진다. 진단 순서는 상대가 죽었는지, 내가 못 나가는지부터 가르는 것이다.

## 2. 빌드는 성공했는데 아이콘이 하나도 없다

> "빌드 성공"은 산출물이 올바르다는 뜻이 아니다.

### 증상

`npm run build`가 경고 하나 없이 성공했다. 그런데 배포된 앱에 PWA 설치 아이콘도 파비콘도 없었다. `dist/`에 이미지 파일이 단 하나도 없었다.

### 원인

직전 리팩터링에서 폴더를 옮겼는데 설정을 그대로 뒀다.

| | 값 |
| --- | --- |
| 실제 폴더 | `public/static/` (리팩터링으로 이동) |
| `vite.config.ts` | `publicDir: 'static'` (방치) |

Vite는 `publicDir` 경로가 없으면 에러도 경고도 없이 건너뛴다. "빌드 성공"이 아무것도 보장하지 않는 상태였다.

### 해결

`publicDir`를 실제 폴더로 고치고 자산을 매니페스트 참조 구조에 맞춰 평탄화했다. `netlify.toml`에 같은 식으로 죽어 있던 리다이렉트도 함께 정리했다.

### 배운 점

경로가 없어도 조용히 넘어가는 설정은 실패를 신호로 바꿔주지 않는다. 파일을 옮기는 리팩터링에서는 검토 기준을 뒤집어야 한다.

- 옮긴 파일 기준으로 훑는다 → 놓친다
- 그 경로를 문자열로 알고 있던 곳 기준으로 훑는다 → 걸린다

## 3. AI 응답이 늦으면 조용히 가짜 일정이 나갔다

> 조용한 폴백은 버그를 품질 문제로 위장한다.

### 증상

AI가 만든 일정의 장소 이름이 전부 "제주도 인기 명소 3" 같은 일반명사로 나왔다. 사용자 눈에는 "AI 추천 품질이 나쁘다"로만 보인다.

### 원인

"로딩 30초 이내" 요구에 맞추려고 27초 예산을 도입하면서 배분을 잘못했다.

| 배분 | 시간 | 문제 |
| --- | --- | --- |
| 주 모델 | 18초 | Gemini 응답이 17~25초라 자주 넘김 |
| 재시도 | 5.5초 | 타임아웃 실패엔 무의미. 503처럼 빠른 실패에만 유효 |

예외가 나면서 기존 폴백(목업 일정)이 반환됐고, 그 폴백이 정상 응답과 구분되지 않고 그대로 화면에 나갔다. 응답 시간이 임계값을 넘나든 게 간헐적 재현의 이유이자 원인을 잡는 실마리였다.

### 틀렸던 가설

프롬프트가 부실해 품질이 낮다고 보고 프롬프트 규칙을 강화했다. 증상은 그대로였다. Gemini가 애초에 호출되지도 못하고 있었으니 프롬프트를 고쳐도 닿지 않는 지점이었다.

### 해결 (당시)

주 모델에 예산 대부분을 몰아주고, 폴백이 나갈 때 `isFallback: true`를 응답에 실어 화면에 드러냈다. 폴백 데이터도 프론트가 쓰던 실제 명소 목록을 서버가 재사용하도록 통일했다.

근본 해결(스트리밍, 비동기 큐)은 하지 않았고 예산 재조정으로 버티는 상태임을 남겼다.

### 후속 (2026-08-16~17)

이 우회는 파이프라인 교체로 대체됐다. 폴백 자체를 없애고, LLM에 일정 전체를 맡기던 구조를 6단계로 나눴다. 예산은 25초, 실측 응답은 7.2초다.

판단이 뒤집혔다. 당시에는 "폴백이 나가는 걸 표시하자"였는데, 지금은 "실재하지 않는 일정을 그럴듯하게 보여주느니 실패를 드러내자"다. 대신 실패를 원인별로 나눈다 — 장소 부족 422, AI 한도 소진 429.

그리고 폴백이 사라지자 숨어 있던 문제가 드러났다. 6번이다.

### 배운 점

타임아웃은 "얼마 안에 끝낼까"만큼 "그 예산을 어떻게 나눌까"가 중요하다. 그리고 폴백은 반드시 폴백임이 드러나야 한다. 안 그러면 원인 조사가 엉뚱한 곳에서 시작된다.

## 4. 브라우저 자동화가 이유 없이 멈춘다

> 프리즈가 아니라 모달 대기 상태였다.

### 증상

자동화로 폼 검증을 확인하다가 클릭 이후 탭이 응답 불능이 됐다. 클릭도 스크린샷도 스크립트 주입도 전부 타임아웃 났고, 서버 로그에는 요청이 하나도 안 찍혔다.

### 원인

검증 실패를 브라우저 모달 `alert()`로 띄우고 있었다. `alert()`는 JS 실행과 렌더러를 동기적으로 블로킹하므로, 자동화가 보내는 후속 명령이 전부 큐에 쌓인 채 타임아웃됐다.

### 해결

이미 있던 Toast 컴포넌트로 교체했다. 새로 만들지 않았다.

여기서 한 번 틀렸다. 처음엔 대상이 3곳이라고 보고했는데 실제로는 `src/` 전체에 10곳이 있었다. grep 범위를 파일 2개로 좁혀놓고 시작한 게 원인이었다. 이후 컴포넌트 단위가 아니라 디렉터리 전체로 다시 훑었다.

파괴적 동작을 확인하는 `confirm()`은 남겨뒀다. 안전장치라서, 대체하려면 별도 확인 모달이 필요하다는 걸 명시했다. 현재 남은 건 일정 삭제 1곳이다.

### 후속 (2026-08-17)

디렉터리 전체를 다시 훑고도 1곳을 놓쳤다. `LoginSignup.tsx`의 회원가입 성공 `alert()`이 그대로 있었다. 자동화가 로그인 화면까지만 가고 회원가입 완료 경로를 밟지 않아 재현되지 않았던 것이다. 전역 Toast를 prop으로 받아 교체했고 `src/` 전체에 호출이 0건임을 확인했다.

같은 실수가 두 번 반복됐다. 처음엔 grep 범위를, 두 번째는 자동화 경로를 좁게 잡았다. 전수 조사의 기준은 코드 범위만이 아니라 실행 경로이기도 하다.

### 배운 점

`alert()`와 `confirm()`은 UX 이전에 테스트 가능성 문제다. 렌더러를 블로킹하는데 죽는 방식이 하필 "타임아웃"이라, 원인이 프론트엔드에 있다는 힌트조차 안 준다.

자동화가 이유 없이 멈추면 네트워크·서버보다 모달 API부터 grep한다.

## 5. 자동완성이 "정확히 일치하는 순간" 후보를 감췄다

> "목록에 있는데 안 나온다"는 데이터가 아니라 조회 조건을 의심하라는 신호다.

### 증상

| 입력 | 결과 |
| --- | --- |
| `도` | 도쿄가 보임 |
| `도쿄` | 사라짐 |

한 글자씩 지우면 다시 보였다.

### 원인

필터 조건에 `d !== destination.trim()`이 있었다. 입력값과 완전히 같은 후보를 제외하는 절이다.

이미 입력한 걸 또 제안하지 말자는 의도였겠지만, 사용자가 지명을 정확히 아는 가장 흔한 경우에 목록이 통째로 비어버렸다.

### 해결

검색 로직을 컴포넌트 밖 순수 함수로 분리하고, 완전일치를 배제하는 대신 최상위로 올리는 랭킹 방식으로 바꿨다. 순서는 완전일치 → 접두 → 포함 → 초성. 겸사겸사 초성 검색도 넣었다.

### 배운 점

"중복 제거"처럼 보이는 방어 조건이 정상 경로를 막는 경우가 있다. 필터에 배제 조건을 넣을 때는 이 조건이 참이 되는 상황이 정말 예외적인지부터 따져야 한다.

## 6. 일정 생성이 통째로 실패 — 조건을 바꿔도 안 풀리는데 "조건을 바꿔 보라"

> 500은 "우리 잘못", 429는 "기다리면 된다". 둘을 섞으면 사용자는 아무것도 못 한다.

### 증상

일정 만들기가 실패하고 화면에는 이 문구만 떴다. 조건을 바꿔도 계속 실패했다.

```
일정을 만들지 못했습니다. 조건을 조금 바꿔 다시 시도해 주세요.
```

### 원인

Gemini 무료 티어 한도 소진. 응답 원문은 이랬다.

```
"code": 429,
"status": "RESOURCE_EXHAUSTED",
"quotaId": "GenerateRequestsPerDayPerProjectPerModel-FreeTier",
"quotaValue": "20"
```

근본 원인은 셋이다.

| # | 원인 |
| --- | --- |
| 1 | 파이프라인 1회가 `후보 추출 1회 + 일수만큼의 설명 호출`을 씀. 3일이면 4회라 하루 20회 한도가 다섯 건이면 소진 |
| 2 | 429가 `500 PLAN_GENERATION_FAILED`에 섞여 있어 "조건을 바꾸라"는 틀린 안내가 나감 |
| 3 | 재시도 로직이 타임아웃 아닌 오류를 즉시 한 번 더 호출. 429는 `retryDelay: 19s`를 주는데 바로 다시 불러 한도만 더 깎음 |

3번(폴백 제거)이 이 문제를 드러나게 했다. 예전엔 가짜 일정이라도 나오던 자리가 그대로 에러가 됐다. 버그가 아니라 설계대로 동작한 결과다.

### 틀렸던 가설

`.env`의 키 이름 불일치를 의심했다(`VITE_GEMINI_API_KEY` vs `GEMINI_API_KEY`). 코드가 두 이름을 모두 읽고 있어 무관했다.

`gemini-2.0-flash`로 모델을 우회하려 했으나 404였다. 폐기된 모델이다.

공식 문서에서 무료 한도 수치를 찾으려 했으나 더 이상 공개하지 않는다. 429 응답 본문이 유일한 실측 근거였다.

### 해결

무료 티어 유지를 전제로 셋을 고쳤다.

1. 설명 호출을 일차별에서 여행 전체 1회 배치로 합침 — 건당 4회 → 2회, 하루 5건 → 10건
2. `QuotaExceededError`를 만들어 429 + `AI_QUOTA_EXCEEDED`로 분리. 태평양시 자정 리셋을 한국시간으로 환산해 재시도 시각까지 안내
3. 쿼터 오류는 재시도 대상에서 제외

리셋 시각은 하드코딩하지 않았다. 서머타임에 따라 한국시간 16시/17시로 움직여서, 고정값을 쓰면 1년의 절반은 틀린 안내가 나간다.

### 검증

- 단위 테스트 22개 추가, 전체 201개 통과
- 실제 HTTP 호출로 확인 — 25초 예산을 태우지 않고 0.55초에 429 반환

```
{"code":"AI_QUOTA_EXCEEDED",
 "message":"오늘 무료 AI 사용량을 다 썼습니다. 한국시간 오후 4시 이후 다시 시도해 주세요."}
HTTP 429, 0.55s
```

### 배운 점

폴백을 지우면 고장이 드러난다. 그런데 드러난 고장을 사용자에게 어떻게 말할지는 별도 설계가 필요하다. 이번엔 "조건을 바꾸라"고 안내해서 바꿔도 안 되는 일을 시켰다.

그리고 무료 한도 문제는 한도를 늘리는 게 아니라 소비량을 줄이는 쪽이 먼저다. 호출 4회를 2회로 만드는 건 코드 한 군데였다.

## 여섯 건에서 반복된 것

네 건(1·2·3·6)은 실패가 실패처럼 보이지 않았다. DNS는 애플리케이션 에러로, 빌드는 성공으로, 폴백은 정상 응답으로, 한도 소진은 서버 오류로 위장했다. 시스템이 조용히 실패하도록 두면 디버깅 시간이 그 대가로 돌아온다.

두 건(4·5)은 조사 범위를 스스로 좁힌 경우다. 파일 2개만 grep했고, 필터 조건 대신 데이터를 의심했다. 증상이 가리키는 곳부터 보게 되는 건 자연스럽지만, 거기서 안 나오면 범위를 넓히는 게 아니라 층을 바꿔야 한다.
