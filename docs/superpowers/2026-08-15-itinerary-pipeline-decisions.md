# 일정 생성 파이프라인 — 판단 기록

- 대상 브랜치: `feat/itinerary-pipeline` (`9b27dad`..`94d1929`, 39커밋)
- 스펙: `docs/superpowers/specs/2026-08-15-itinerary-generation-design.md`

실행 중 내린 판단을 남긴다. 각 항목은 무엇을 정했는지, 왜 그렇게 정했는지, 틀렸을 때 무엇을 잃는지를 함께 적는다.
"틀렸을 때 비용"이 있는 이유는 나중에 되돌릴지 판단하려면 그게 필요하기 때문이다.

---

## 1. 무엇을 왜 바꿨나

### 출발점

사용자가 지목한 문제 네 가지다.

1. 같은 장소가 1일차와 2·3일차에 중복해서 나온다
2. 동선을 고려하지 않는다
3. 늘 같은 곳만 추천한다
4. 식당이 "소문난 맛집" 같은 실체 없는 이름으로 나온다

원인은 구조에 있었다. 기존 구현은 Gemini에게 "일정 전체를 짜 줘"라고 한 번 물어보고 그 텍스트를 그대로 화면에 뿌렸다. 중복 금지도, 동선도, 실재하는 상호명도 전부 프롬프트 문장으로만 부탁하고 있었고, 검증하는 코드가 없었다. 모델이 지키면 지켜지고 안 지키면 그대로 나갔다.

### 바꾼 구조

책임을 쪼개서, 검증 가능한 것은 코드가 맡고 모델은 코드가 못 하는 것만 맡게 했다.

```
1. Gemini        후보 장소 이름만 제안 (필요량의 2.5배 오버샘플링)
2. Kakao Local   각 이름이 실재하는지 조회 → 실좌표·실place id 확보. 없으면 탈락
3. k-means       정원 제약 클러스터링으로 날짜별 배정 (한 장소는 한 번만)
4. TSP           하루 안 방문 순서 결정 (n≤8 완전탐색, 초과 시 nearest neighbour)
5. 스케줄러      이동·체류 시간으로 시각 배치, 식사는 카카오 주변 검색으로 삽입
6. Gemini        각 활동의 설명 문장만 작성
```

네 가지 불만이 각각 어디서 해결되는지:

| 불만 | 해결 지점 |
|---|---|
| 중복 | 3단계 클러스터링은 한 장소를 한 날에만 배정한다. 전역 `usedIds` 집합이 식당 선택까지 공유된다 |
| 동선 | 4단계 TSP + 날짜 순서 최적화. 이동 시간이 스케줄에 실제로 반영된다 |
| 반복 | 1단계 오버샘플링 + 2단계 검증 탈락으로 후보 풀이 매번 달라진다 |
| 가짜 식당 | 식당은 모델이 아니라 카카오 주변 검색에서 온다. 실재하지 않으면 애초에 나올 수 없다 |

### 채택하지 않은 것

- 폴백 일정 제거. 기존에는 생성이 실패하면 하드코딩된 가짜 일정을 조용히 내보냈다. 사용자가 그걸 진짜로 받아들이는 게 더 나쁘다고 보고 전부 걷어냈다. 지금은 명시적으로 실패한다.
- 구글 Places를 검증용으로 쓰는 안. 국내 장소 커버리지와 무료 할당량 모두 카카오가 낫다. 구글은 기존대로 사진 조회에만 쓴다.
- 30초 상한 완화. 사용자가 유지하기로 정했다. 이 제약이 후보 개수 상한과 재시도 정책을 전부 결정했다.

## 2. 실행 중 내린 판단

번호는 작업 원장의 룰링 번호다.

### 계획 자체의 결함을 고친 것

R-5 — 계획서에 적힌 이름 정규화 정규식 `/[\s\W_]/gu`가 한글을 전부 지운다. `"성산일출봉"`이 빈 문자열이 되어, 중복 제거가 모든 한국어 장소를 같은 것으로 판정했을 것이다. `/[^\p{L}\p{N}]/gu`로 바꿨다. 구현자가 1차로 넣은 "제거할 문자 열거" 방식은 괄호를 못 걸러 `"우진해장국(본점)"`이 남았다. 카카오 상호명에 흔한 형태라 채택하지 않았다.
틀렸을 때 비용: 구두점만 다른 서로 다른 장소가 같다고 판정될 수 있다.

R-1, R-2, R-4 — 계획서의 테스트 기대값 세 건이 수학적으로 성립하지 않았다. 완전 타이인 순회 순서, 하한 규칙과 시간 제한이 동시에 성립할 수 없는 픽스처, 구속력 없는 테스트 개수 주석. 각각 고치거나 구속 조건에서 뺐다.

### 설계 판단

R-8 — 저녁 슬롯을 창 안으로 끌어내리지 않는다. 하한 규칙이 하루를 19:30 너머로 밀어낸 날에 저녁을 창 안으로 당기면 진행 중인 활동 안에 박힌다. 창 준수보다 겹침 없음을 택했다.
틀렸을 때 비용: 병적으로 긴 날에는 저녁이 19:30을 넘겨 표시된다.

R-9 — 카테고리 매핑에서 확정 코드가 이름 부분 문자열보다 우선한다. `"여행 > 숙박 > 산장,별장"`이 `"산"`에 걸려 자연으로 분류됐고, 카테고리가 체류 시간을 정하므로 하루가 통째로 밀렸다. 다만 이름 검사를 없앨 수는 없다 — 실제 API 확인 결과 성산일출봉은 카테고리 코드가 빈 문자열로 온다.
틀렸을 때 비용: `AT4`·빈 코드 구간에는 여전히 오분류 여지가 남는다.

R-11 — 후보 상한 60개를 유지한다. 10일 빡빡하게의 순수 필요량(80)보다 낮지만, 한 응답에 80개 이상을 요구하면 30초 예산을 넘길 위험이 크다.
틀렸을 때 비용: 장기 고강도 여행이 기대보다 얇게 나온다.

R-12 — 설명을 인덱스로 짝짓지 않고 이름으로 대조한다. 모델이 개수만 맞추고 순서를 바꿔 돌려주면 A 장소에 B 설명이 조용히 붙었고, 이를 막던 건 프롬프트 문장 한 줄이었다. 스키마에 `title`을 필수로 넣고 대조해 어긋나면 그 날만 최소 설명으로 내린다. 화면에 나가는 이름은 여전히 카카오가 준 값이고, 모델 응답은 정렬 확인용으로만 쓴다.
틀렸을 때 비용: 모델이 이름을 정확히 옮기지 못하면 정상 응답도 최소 설명으로 강등된다.

R-16 — 후보 추출이 타임아웃으로 실패하면 재시도하지 않고, 그 외 오류만 재시도한다. 처음에는 총 30초에서 역산해 재시도 예산을 5초로 줄였는데, 그 결과 4회 중 3회가 실패했다(실측 지연 6.1초·10.4초). 느린 요청은 다시 해도 느리다 — 그 쓸모없는 재시도 자리를 예산에 남겨두느라 1차 예산까지 작아진 것이 원인이었다. 구분한 뒤 1차 예산을 14초로 늘렸다.
틀렸을 때 비용: 일시적 오류의 재시도 성공률이 낮아진다.

R-22 — 수정 요청의 "장소 바꿔줘"를 코드가 강제한다. 제외 지시가 자유 텍스트 `comments`에만 실려 후보 LLM 프롬프트로만 갔는데, 식당은 후보 LLM이 아니라 카카오 주변 검색에서 온다. 제외가 식사 선택에 닿는 코드 경로가 아예 없었다. 확률 문제가 아니라 구조적 구멍이다.
틀렸을 때 비용: 사용자가 필수로 지정한 곳은 "장소 바꿔줘" 후에도 남는다(의도된 동작).

R-32 — 하루 종료 규칙을 관광 시간으로만 판단하고 식사 시간은 제외한다. 겹침 수정의 부수효과로 빡빡하게 일정이 5곳에서 4곳으로 줄었는데, 4는 빡빡하게의 하한이라 강도 선택이 무의미해진다. 잘라내던 초과분의 상당 부분이 관광이 아니라 점심이었다. 장소를 잃는 건 눈에 보이고, 마지막 활동이 18:00 대신 18:26에 끝나는 건 보이지 않는다.
틀렸을 때 비용: 하루가 규칙 문언보다 최대 식사 시간만큼 늦게 끝난다.

R-33 — 수정 의도 판정에서 `별로`를 술어형(`별로예요`/`별로네요`/`별로였`)으로 좁힌다. `별로 + 부정`은 한국어의 일상적인 "많지 않다" 표현이라 "시간이 별로 없어요"류가 전부 전 일정 재금지를 유발했다. 오탐 비용(사용자가 좋아한 장소를 조용히 버림)이 누락 비용보다 훨씬 크다.
틀렸을 때 비용: `별로에요`·`별론데` 같은 변형이 누락된다.

### 되돌린 내 판단

R-15 → R-16 — 재시도 예산 축소가 라이브 실패율 75%를 만들었다. 관측 지연 분포를 보지 않고 상한에서 역산한 것이 원인이었다.

M2 → R-34 — 겹침 불변식 정의가 두 곳에 중복돼 있어 "하나로 합쳐라"고 지시했는데, 그 결과 `insertMeals`가 결과를 강제하는 함수와 테스트가 검증에 쓰는 함수가 같아져 불변식이 실패할 수 없게 됐다. 이동 시간 항을 지워도 148개 테스트가 전부 통과했다. 프로덕션 공유 헬퍼는 유지하고 테스트만 이동 시간을 독립 계산하도록 바꿨다.

## 3. 검증

### 라이브 (커밋 `2c0051a`, 제주도 2박3일 / 빡빡하게 / 자차 / 필수 성산일출봉)

12초, 활동 21개, 중복 0건, 성산일출봉 포함 및 필수 표시, 주차장 POI 없음.
식당은 전부 실재하는 상호였다 — 고궁보말손칼국수, 오는정김밥, 네거리식당, 저지면옥 본점.
클러스터도 깨끗하게 갈렸다 — 1일차 서부·중앙, 2일차 서귀포, 3일차 서부 목장권.

### 입력 검증 (LLM 호출 없이 반환되므로 쿼터 소모 없음)

빈 목적지 → `DESTINATION_REQUIRED`, `"어제"`/`"내일"` → `TRIP_DATES_INVALID`, 1년 범위 → `TRIP_TOO_LONG`, 뒤집힌 날짜 → `TRIP_DATES_INVALID`. 전부 HTTP 400. 14일 요청은 정상 통과.

### 최종

179개 테스트 / 14개 파일 통과, `tsc --noEmit` 통과, 빌드 통과.

테스트가 실제로 판별력이 있는지는 별도로 확인했다. 이 프로젝트에서 "코드를 지워도 통과하는 테스트"를 여러 번 잡았기 때문에, 주요 항목은 격리된 worktree에서 프로덕션 코드를 일부러 망가뜨려 해당 테스트가 실패하는지 확인했다.

## 4. 남은 것

### 배포 전 결정 필요

`netlify.toml`에 함수 타임아웃 설정이 없다. Netlify 동기 함수 기본 상한은 10초인데 파이프라인 예산은 25초 + 사진 2.5초다. 실측 9.5~16.5초. 기존 코드도 27초를 잡고 있었으므로 이번 브랜치가 만든 문제는 아니지만, 배포하면 여기서 먼저 걸린다.

### 알려진 제약

- `tsconfig.json`에 `strict` 계열 설정이 없다. `strictNullChecks`가 꺼져 있어 `if (!x.ok)`가 타입을 좁히지 않는다. 코드는 `x.ok === false`로 우회했다. 켜면 기존 코드 전체가 걸리므로 별도 작업이다.
- `wantsDifferentPlaces`는 부분 문자열 매칭이다. 키워드를 아무리 조정해도 이 계열의 오분류는 남는다. 근본 해결은 UI에 "장소를 전부 바꿀까요?" 확인 단계를 두는 것이다.
- 병적으로 긴 이동 거리에서는 하루가 자정을 넘기고 `formatTime`의 `% 24`가 "오전 01:35"로 렌더한다. 하한 우선 규칙이 시간 제한을 이기는 기존 동작이며, 카카오로 검증된 국내 단일 지역 후보에서는 도달 가능성이 낮다.
- 버려진 Gemini 요청에 `AbortController`가 걸려 있지 않다. 결과를 폐기하고 공유 상태를 건드리지 않으므로 정합성 문제는 아니고 쿼터 낭비다.
- Gemini 무료 티어는 일일 20회다. 파이프라인 1회 실행이 `1 + 일수` 회를 쓴다(2박3일이면 4회, 14일이면 15회).

### 트러블슈팅

원인 규명이 오래 걸렸거나 첫 가설이 틀렸던 건은 `~/Project/TROUBLESHOOTING.md`에 TS-025 ~ TS-029로 기록했다.
