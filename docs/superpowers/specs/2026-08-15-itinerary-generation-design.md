# 일정 생성 파이프라인 재설계

작성일: 2026-08-15
상태: 승인됨 (구현 대기)

## 1. 배경

시연 영상에서 생성된 제주도 2박 3일 일정이 실제 여행에 쓸 수 없는 수준이었다. 확인된 증상은 네 가지다.

1. 같은 장소가 1일차와 2·3일차에 반복해서 등장한다
2. 동선을 고려하지 않아 하루 안에서 지역을 오간다
3. 목적지가 같으면 매번 같은 곳만 추천한다
4. 맛집이 "소문난 맛집" 같은 일반명사로 나온다

## 2. 진단

### 2.1 영상에 나온 일정은 AI 출력이 아니다

`createFallbackPlan()`이 만든 하드코딩 템플릿이다. 영상 속 문자열이 코드에 그대로 있다.

| 영상 문구 | 코드 위치 |
|---|---|
| 제주도 아침 식사 | `netlify/functions/generate-plan.ts:221` |
| 제주도을(를) 대표하는 성산일출봉입니다. 시간을 넉넉히 두고 둘러보세요. | `generate-plan.ts:243` |
| 추천 한식/현지식 소문난 맛집 | `generate-plan.ts:257` |
| 제주도 감성 저녁 맛집 | `generate-plan.ts:272` |
| 제주도에서의 특별한 하루 - 1일차 | `generate-plan.ts:285` |

같은 코드가 `server/server.ts:318-420`에 복제되어 있다.

### 2.2 중복은 계산상 필연이었다

```
spotNameFor = knownSpots[(day - 1 + s) % knownSpots.length]   // generate-plan.ts:213
제주도 knownSpots = ["성산일출봉", "한라산", "협재해수욕장"]     // recommendedSpots.ts:111
"빡빡하게" 선택 시 spotsPerDay = round((4 + 8) / 2) = 6        // generate-plan.ts:165-167
```

3개 목록에서 6개를 뽑으므로 하루에 같은 장소가 정확히 두 번씩 들어간다.

### 2.3 폴백이 뜬 이유는 타임아웃이다

`GENERATION_BUDGET_MS = 27_000`, 클라이언트는 `GENERATION_TIMEOUT_MS`에 abort한다(`PlannerFlow.tsx:188`). 주 모델에 약 24초가 주어지는데, 3일치 27개 활동의 설명문까지 한 번에 생성하느라 출력 토큰이 4,000개를 넘어 그 안에 못 끝냈다.

### 2.4 프롬프트 강화로는 풀리지 않는다

현재 프롬프트에는 이미 해당 지시가 들어 있다.

- 9항: 같은 날 활동은 지리적으로 인접한 하나의 권역으로 묶어라
- 11항: 앞뒤 장소가 가장 가까운 순서로 시간순 정렬해라
- 12항: "로컬 맛집", "소문난 맛집" 같은 표현 절대 금지
- 13항: 맛집은 대표 메뉴를 구체적으로 적어라

지켜지지 않았다. 검증 가능한 제약은 부탁이 아니라 코드가 강제해야 한다.

## 3. 목표와 비목표

### 목표

- 한 여행 안에서 같은 장소가 두 번 나오지 않는다
- 하루 활동이 지리적으로 인접한 순서로 배치된다
- 모든 장소가 실존하며 실제 좌표를 가진다
- 식당·카페는 실제 상호명으로 나온다
- 같은 조건으로 다시 생성하면 다른 일정이 나온다
- 30초 안에 응답한다
- 무료 API 한도 안에서 동작한다

### 비목표

- 해외 목적지. 국내 전용으로 한정한다
- 숙소 추천
- 평점·영업시간 기반 필터링. Google Places Enterprise 등급이라 무료 한도(월 1,000건) 밖이다
- 실시간 경로 안내. Directions API는 별도 SKU다

## 4. 제약

| 항목 | 값 | 근거 |
|---|---|---|
| 응답 시간 | 30초 이내 | 기존 UX 유지 |
| 장소 검증 API | 카카오 로컬, 키워드·카테고리 각 일 10만 / 전체 월 300만 무료 | 국내 데이터 품질, 무료 한도 |
| 사진 API | Google Places, Essentials 등급만 (월 1만건) | `photos`, `location`, `formattedAddress`는 Essentials. `rating` 이상은 Enterprise |
| LLM | Gemini 2.5 Flash, `thinkingBudget: 0` | 기존 유지 |

카카오 무료 쿼터에는 조건이 있다. 2026년 7월 21일부터, 개발자 계정 기준 첫 번째로 카카오맵 API를 활성화한 앱 하나만 무료 쿼터를 받는다. 두 번째 앱부터는 비즈월렛 연결 후 사용량 과금이며, 장소검색 단가는 2원/건이다. 한 번 정해지면 다른 앱으로 옮길 수 없다.

`tripmate` 앱은 무료 쿼터 대상임을 실제 호출로 확인했다(2026-08-15). 키워드 검색, FD6·AT4 카테고리 검색 모두 200 응답과 정상 데이터를 반환했다.

## 5. 아키텍처

파이프라인 로직이 `netlify/functions/generate-plan.ts`(557줄)와 `server/server.ts`(915줄)에 복제되어 있다. 새 파이프라인은 더 크므로 두 벌로 유지하면 반드시 어긋난다. 공유 모듈로 추출하고 두 진입점은 얇은 핸들러만 남긴다.

## 6. 파이프라인

| 단계 | 하는 일 | 예산 |
|---|---|---|
| 1 | LLM 1회 — 장소 이름만. 설명 없음 | 8초 |
| 2 | 카카오 로컬 병렬 조회 — 실존 검증, 실좌표, 카테고리, 주소 | 3초 |
| 3 | 코드 — 중복 제거, 권역 배정, 순서 정렬, 시간·식사 배치 | 0초 |
| 4 | LLM 날짜 수만큼 병렬 — 확정된 장소에 설명·테마만 | 10초 |
| 5 | 사진 병렬 조회 | 3초 |

합 24초. 30초 예산에 6초 여유. 각 단계에 개별 타임아웃을 둔다.

### 6.1 데이터 계약

```ts
type PlaceCategory = "관광" | "자연" | "문화" | "쇼핑" | "맛집" | "카페" | "액티비티";

// 1단계 산출
type Candidate = {
  name: string;
  category: PlaceCategory;
};

// 2단계 산출
type ResolvedPlace = {
  id: string;          // 공급자 고유 id
  name: string;        // 실제 상호명
  lat: number;
  lng: number;
  category: PlaceCategory;
  address: string;     // 도로명 주소
  placeUrl?: string;
  mustVisit: boolean;
};

// 3단계 산출
type ScheduledActivity = {
  place: ResolvedPlace;
  startMinutes: number;          // 자정 기준 분
  stayMinutes: number;
  travelFromPrevMinutes: number;
  isMeal: boolean;
  mealType?: "아침" | "점심" | "저녁";
};

type ScheduledDay = {
  day: number;
  activities: ScheduledActivity[];
};
```

4단계가 `theme`, `description`, `tags`를 채우고, 5단계가 `imageUrl`을 채운다. 최종 응답 형태는 기존 `TravelPlan`(`src/types.ts`)을 유지해 프론트 변경을 최소화한다. `isFallback`만 제거하고 `narrationDegraded?: boolean`을 추가한다.

### 6.2 1단계 — 후보 추출

LLM에게 장소 이름과 카테고리만 요청한다. 설명문을 쓰지 않으므로 출력 토큰이 40개 항목 기준 600토큰 수준으로 떨어진다.

요청 개수는 `필요량 × 2.5`로 잡고 60개로 클램프한다. 필요량은 `일수 × 강도 상한`이다. 2박 3일 빡빡하게면 `3 × 8 = 24`이므로 60개, 여유롭게면 `3 × 3 = 9`이므로 23개를 요청한다.

다양성은 여기서 확보한다. 필요량보다 넉넉히 받아 3단계에서 골라 쓰므로, 후보 풀이 흔들리면 결과가 달라진다.

필수 방문지는 목록 맨 앞에 무조건 포함시킨다.

### 6.3 2단계 — 장소 검증

각 후보를 `PlaceResolver.resolve(name, destination)`으로 조회한다. 카카오 로컬 키워드 검색을 쓰고, 결과가 없으면 그 후보는 버린다.

#### 결과가 없다는 것만으로는 부족하다

실제 호출로 확인한 사실이다. "제주도 소문난 맛집"을 검색하면 빈 결과가 아니라 아래가 돌아온다.

```
소문난맛집            제주시 애월읍 애월해안로 945-2
군산소문난해물칼국수     제주시 천수로 16
소문난할머니집         제주시 조천읍 남조로 2367
```

`소문난맛집`이라는 상호의 가게가 실재한다. 카카오는 없는 것을 없다고 하지 않고 비슷한 것을 찾아준다. 따라서 "검색 결과가 없으면 버린다"만으로는 일반명사가 통과한다.

식당·카페는 LLM이 아니라 카테고리 검색으로 뽑으므로 이런 쿼리가 들어갈 일이 없다. 위험한 쪽은 관광지 후보다. LLM이 "제주 유명 오름" 같은 이름을 내놓으면 엉뚱한 장소에 매칭된다. 두 겹으로 막는다.

1. 조회 전 차단 — 후보명에 일반명사가 포함되면 조회하지 않고 버린다. 차단 목록: 맛집, 카페, 명소, 스팟, 추천, 로컬, 현지, 유명한, 인기, 전망 좋은, 분위기 좋은
2. 조회 후 검증 — 요청한 이름과 반환된 `place_name`을 정규화(공백·특수문자 제거, 소문자화)한 뒤 비교한다. 요청명이 결과명에 포함되거나 그 반대인 경우만 통과시키고, 아니면 버린다

예: 요청 "성산일출봉" → 결과 "성산일출봉" 통과. 요청 "제주유명오름" → 결과 "새별오름" 탈락.

#### 카테고리 코드가 비어 올 수 있다

성산일출봉은 `category_group_code`가 빈 문자열로 온다. 코드가 비면 `category_name` 문자열로 분류한다.

`PlaceResolver`는 인터페이스로 두어 공급자를 교체할 수 있게 한다.

```ts
interface PlaceResolver {
  resolve(name: string, destination: string): Promise<ResolvedPlace | null>;
  searchNearby(
    lat: number,
    lng: number,
    categoryCode: "FD6" | "CE7" | "AT4",
    radiusMeters: number,
  ): Promise<ResolvedPlace[]>;
}
```

카카오 카테고리 코드를 내부 `PlaceCategory`로 매핑한다.

| 카카오 | 내부 |
|---|---|
| FD6 음식점 | 맛집 |
| CE7 카페 | 카페 |
| AT4 관광명소 | 관광 |
| CT1 문화시설 | 문화 |
| MT1 대형마트 | 쇼핑 |
| 그 외 | 관광 |

카카오가 반환하는 `category_name` 문자열에 "자연", "산", "해수욕장", "폭포", "오름", "공원"이 포함되면 위 매핑보다 우선해 자연으로 분류한다.

### 6.4 3단계 — 확정 (핵심)

외부 호출 없이 코드만으로 결정한다. 여기서 네 가지 목표가 불변식이 된다.

#### 중복 제거

정규화된 이름이 일치하거나 haversine 거리 50m 이내면 동일 장소로 본다. 정규화는 공백·특수문자 제거 후 소문자화다. 여행 전체에 전역 집합 하나를 쓴다. 같은 장소가 서로 다른 날짜에 들어가는 것이 구조적으로 불가능해진다.

#### 권역 배정

용량 제한 k-means를 쓴다. `k = 여행 일수`, 클러스터 정원 = 강도 상한(여유롭게 3, 빡빡하게 8).

1. 초기 중심은 greedy farthest-point로 결정론적으로 고른다. 난수를 쓰지 않으므로 테스트가 재현된다
2. 필수 방문지를 각자 가장 가까운 초기 중심에 고정 배정하고 정원에서 차감한다
3. 최대 20회 반복
   - 각 점을 "가장 가까운 중심까지의 거리"가 짧은 순으로 처리하며, 가장 가까운 중심에 배정한다. 정원이 찼으면 다음으로 가까운 여유 클러스터로 넘긴다
   - 중심을 소속 점들의 평균으로 갱신한다
   - 배정이 바뀌지 않으면 종료한다
4. 강도 하한(여유롭게 1, 빡빡하게 4)에 미달하는 클러스터는 미배정 후보 중 그 중심에 가장 가까운 것으로 채운다. 후보가 없으면 `searchNearby(중심, "AT4", 5000)`으로 보충한다

AT4 보충의 품질은 기대치를 낮춰야 한다. 제주시청 반경 5km로 실제 호출한 결과는 국수문화거리, 전농로왕벚꽃거리, 성안올레 3코스, 칠성로쇼핑거리였다. 거리순 정렬이라 가까운 것부터 나오고 여행지로서의 매력도는 반영되지 않는다. 마지막 수단으로만 쓴다.

#### 날짜 순서

클러스터 중심 `k`개에 대해 최단 순회를 구한다. `k`는 실질적으로 8 이하이므로 완전탐색한다.

#### 하루 안 순서

클러스터 정원이 8이므로 활동 수가 8을 넘지 않는다. `n! ≤ 40,320`이라 거리행렬을 미리 계산하고 완전탐색한다. 근사 알고리즘이 필요 없다.

시작점은 전날 마지막 장소에 가장 가까운 점으로 잡는다. 1일차는 클러스터 중심에 가장 가까운 점이다.

### 6.5 3단계 — 시간 배정과 식사

체류시간 기본값(분).

| 카테고리 | 분 |
|---|---|
| 자연, 액티비티 | 120 |
| 관광, 문화, 쇼핑 | 90 |
| 카페 | 60 |

식사 체류시간은 아침 45, 점심 60, 저녁 90.

이동시간은 haversine 직선거리에 우회계수 1.3을 곱하고 이동수단 평균속도로 나눈다. 도보 4km/h, 대중교통 20km/h, 자차 40km/h. 최소 10분으로 하한을 둔다.

배치 규칙.

- 첫 일반 활동을 09:00에 시작한다
- 아침은 08:00, 첫 활동 반경 1km 안에서 `searchNearby(FD6 또는 CE7)`로 고른다
- 점심은 누적 시각이 12:00을 넘기는 첫 지점 직전에 삽입한다. 13:30을 넘기면 13:30에 강제 삽입한다
- 저녁은 마지막 활동 종료 후, 18:00~19:30 범위로 클램프한다
- 식당은 그 시점 위치 반경 1km 안에서 고른다. 이미 쓴 장소는 제외한다
- 표시 시각은 5분 단위로 반올림한다

식당을 LLM에게 묻지 않으므로 일반명사가 나올 경로가 없다.

#### 하루 길이로 개수를 조정한다

권역 배정은 클러스터를 정원까지 채우므로 그대로 두면 매일 상한 개수가 된다. 그러면 이동이 먼 날에도 억지로 숫자를 채우게 된다.

시간을 배정한 뒤 하루가 09:00~19:30(630분)을 넘으면 뒤쪽 일반 활동부터 하나씩 제거하고 다시 계산한다. 강도 하한에 도달하면 멈추고 그 상태로 둔다. 이동 거리가 긴 날은 자연히 활동 수가 줄고, 장소가 모여 있는 날은 상한까지 채워진다. 날마다 다른 밀도가 규칙이 아니라 결과로 나온다.

제거된 장소는 폐기한다. 다른 날로 옮기면 그 날의 동선이 깨진다.

### 6.6 4단계 — 설명 생성

확정된 날짜별 장소 목록을 넘겨 `theme`, 날짜 `description`, 활동별 `description`, `tags`만 생성한다. 날짜별 독립 호출이라 3일이면 3회 병렬이다.

장소 선정 권한이 없으므로 프롬프트에서 동선·실명 관련 조항 9~14를 전부 삭제한다. 남는 지시는 톤과 길이(2~3문장, 120자 이내)뿐이다.

### 6.7 5단계 — 사진

기존 `fetchRealPlacePhotoRef`를 유지하되, 2단계에서 이미 정확한 상호명을 확보했으므로 검색 정확도가 올라간다. 요청 필드는 `photos`로 한정해 Essentials 등급을 유지한다. 실패하면 기존 카테고리 목업 이미지로 폴백한다.

## 7. 실패 처리

가짜 일정을 만들어 보여주는 폴백을 제거한다. 사용자가 AI 추천으로 오인하는 것이 이번 문제의 최대 원인이었다.

| 단계 | 실패 시 |
|---|---|
| 1 | 1회 재시도. 그래도 실패하면 에러 응답 |
| 2 | 개별 장소는 버린다. 남은 수가 `일수 × 강도 하한`에 미달하면 `searchNearby(AT4)`로 보충. 그래도 미달이면 에러 응답 |
| 3 | 순수 계산이라 실패하지 않는다. 예외는 버그이므로 그대로 던진다 |
| 4 | 날짜별 독립이므로 실패한 날만 최소 설명으로 채운다. 응답에 `narrationDegraded: true`를 실어 클라이언트가 "설명 다시 생성" 버튼을 띄운다 |
| 5 | 목업 이미지로 폴백한다 |

4단계 최소 설명은 실제 데이터로만 구성한다.

- `theme`: `${destination} ${day}일차`
- 날짜 `description`: 그날 장소들의 주소에서 추출한 시·군·구 목록
- 활동 `description`: `${address}에 있는 ${category}입니다.`

가짜 장소가 아니라 설명이 짧을 뿐이므로 사용자를 속이지 않는다.

에러 응답은 `.claude/standards/api-contract.md` 형식을 따른다.

```jsonc
{
  "success": false,
  "data": null,
  "error": {
    "code": "PLAN_GENERATION_FAILED",
    "message": "일정을 만들지 못했습니다. 조건을 조금 바꿔 다시 시도해 주세요.",
    "field": null
  }
}
```

## 9. 테스트

`routing.ts`, `schedule.ts`, `geo.ts`가 순수 함수이므로 실제 API 없이 검증한다. `PlaceResolver`는 인터페이스라 고정 픽스처로 모킹한다. 기존 vitest 설정(`tests/`)에 붙인다.

`tests/itinerary/routing.test.ts`

- 같은 장소가 서로 다른 두 날짜에 배정되지 않는다 (2.2 회귀 테스트)
- 후보 수가 필요량보다 적어도 중복으로 채우지 않는다 (2.2 회귀 테스트)
- 하루 안 총 이동거리가 같은 장소 집합의 무작위 순열 100회보다 항상 짧거나 같다
- 클러스터별 활동 수가 강도 범위 안에 든다
- 필수 방문지가 결과에 반드시 포함되고 `mustVisit: true`다
- 같은 입력에 같은 출력을 낸다

`tests/itinerary/schedule.test.ts`

- 매일 아침·점심·저녁이 각 1개씩 있다
- 점심 시작 시각이 11:30~13:30 안이다
- 저녁 시작 시각이 18:00~19:30 안이다
- 활동 시작 시각이 단조 증가한다
- 이동수단을 도보로 바꾸면 총 이동시간이 자차보다 길다

`tests/itinerary/geo.test.ts`

- haversine이 알려진 두 좌표 쌍에서 기대값 오차 1% 이내다

`tests/places/kakao.test.ts`

- 카카오 응답 JSON 픽스처를 `ResolvedPlace`로 올바르게 매핑한다
- 검색 결과가 비면 `null`을 반환한다

## 10. 비용

2박 3일 기준. 여유롭게와 빡빡하게의 범위로 적는다.

| 항목 | 일정 1개당 | 무료 한도 | 여유 |
|---|---|---|---|
| 카카오 로컬 | 32~69건 (후보 조회 23~60 + 식사 검색 9) | 일 10만 | 하루 1,400개 일정 |
| Google Places 사진 | 18~33건 (활동 수만큼) | 월 1만 (Essentials) | 월 300개 일정 |
| Gemini 호출 | 1 + 날짜 수 = 4회 | — | 총 출력 토큰은 현재보다 감소 |

Google Places가 병목이다. 월 300개를 넘길 조짐이 보이면 사진을 카카오 `place_url` 링크로 대체하거나 생성 결과에 캐시를 둔다. 현 단계에서는 조치하지 않는다.

## 13. 열린 사항

프론트 로딩 화면을 단계별 진행 표시로 바꿀지는 이번 범위에 넣지 않았다. 지금은 잔여 시간 카운트다운만 보여주는데, 파이프라인이 4단계로 나뉘므로 "장소 찾는 중 / 동선 짜는 중 / 설명 쓰는 중"을 보여줄 수 있다. 별도 작업으로 다룬다.
