<a id="adr-1"></a>
## ADR-1 · thinking 모드를 끄고 응답 속도를 확보한다

### 문제 상황

"로딩 30초 이내"라는 요구가 있었는데 Netlify Functions는 동기 호출이라 실행시간 상한이 빡빡하다. Gemini 2.5 Flash 계열은 thinking(내부 추론)이 기본으로 켜져 있는데, 이것 때문에 502/504 타임아웃이 반복됐다.

### 검토한 선택지

1. thinking을 유지하고 타임아웃을 늘린다
2. thinking을 끄고 속도를 확보한다
3. 더 가벼운 모델로 완전히 갈아탄다

### 결정

2번. `thinkingConfig: { thinkingBudget: 0 }`으로 껐다. 여기에 더해 주 모델이 실패하면 보조 모델, 그것도 실패하면 주 모델로 한 번 더 가는 3단계 폴백 체인을 붙였다.

### 이유

서버리스 실행시간 상한은 플랫폼 제약이라 늘릴 수가 없었다. 응답을 JSON 스키마로 강제하는 구조라 thinking이 품질에 주는 이득은 크지 않은데 지연에는 직접 영향을 줬다.

### 결과

502/504는 없어졌다. 다만 "thinking만 끄면 끝"이라는 예상은 절반만 맞았고, 이후 응답 시간이 17~25초로 흔들리는 게 드러나 타임아웃 예산을 다시 손봐야 했다(TS-012).

모델 폴백 체인은 나중에 걷어냈다. 모델을 갈아타는 방식으로는 실패 원인을 알 수가 없다. 쿼터 소진이든 타임아웃이든 전부 "보조 모델로 넘어감"으로 뭉개진다. thinking 비활성화는 지금도 두 호출 모두에 그대로 적용돼 있다.

<a id="adr-2"></a>
## ADR-2 · Supabase를 브라우저에서 직접 호출하고 RLS로 통제한다

### 문제 상황

일정 저장·조회·삭제는 로그인한 사용자별 데이터라 인증과 묶인 DB 접근이 필요했다. Supabase의 anon key는 애초에 클라이언트 노출을 전제로 만들어진 키이고, 대신 RLS로 접근을 통제하는 구조다.

### 검토한 선택지

1. 자체 API 서버를 두고 그 뒤에서만 Supabase를 호출한다
2. 브라우저에서 직접 CRUD하고 RLS 정책으로 소유권을 통제한다
3. 읽기는 직접, 쓰기는 서버 경유로 나눈다

### 결정

2번. 브라우저가 직접 호출하고 소유권 검사를 RLS에 위임했다.

### 이유

API 계층을 하나 더 두면 서버가 Supabase 요청을 그대로 넘기는 얇은 프록시가 돼서 코드만 늘어난다. anon key + RLS 조합 자체가 직접 호출을 전제로 설계된 거라, 서버를 하나 더 만드는 것보다 RLS 정책을 촘촘히 짜는 게 맞는 방향이라고 봤다.

반대로 Gemini와 Places 키는 공개를 전제하지 않으니 서버 경유로 남겼다. 결과적으로 DB는 직접, 외부 API는 서버 경유인 비대칭 구조가 됐다.

### 결과

RLS로 통제되는 한 보안상 문제는 없다. 다만 이 구조가 다른 사고의 진단을 늦추는 부작용이 있었다. Supabase가 일시정지됐을 때(TS-003) "서버 로그가 비어 있다"는 신호가 구조를 모르면 헷갈리는 단서였다.

<a id="adr-3"></a>
## ADR-3 · 명소 추천은 정적 데이터로 고정한다

### 문제 상황

필수 방문지 추천에 쓸 실제 장소명이 필요했다. Google Places API는 이미 사진 조회용으로 연동돼 있었다.

### 검토한 선택지

1. 장소명도 Places 텍스트 검색으로 매번 실시간 조회한다
2. 목적지별 정적 데이터셋을 코드에 직접 넣는다

### 결정

2번. 장소명은 정적 데이터로 고정했다.

### 이유

Places 텍스트 검색은 "진짜 유명한 곳"을 보장해주지 않는다. 리뷰 수나 카테고리 랭킹이 의도와 다르게 나올 수 있고, 매 요청마다 과금과 지연이 붙는다. 어설픈 실시간 데이터보다 신뢰를 지키는 쪽을 택했다. 목록에 없는 목적지는 빈 배열을 돌려서 추천 줄 자체를 숨긴다. 그럴듯한 일반 문구로 채우면 추천 자체의 신뢰가 깨지기 때문이다.

### 결과

목적지가 101곳으로 제한되고 목록 밖 지명은 추천이 안 뜬다. 의도한 제한이라 그대로 뒀다.

사진 쪽은 나중에 방향이 바뀌었다. Google Maps Platform이 결제 계정 등록을 요구하는데 이 프로젝트는 무료 범위 안에서만 운영하기로 해서, 지금은 카테고리별 목업 이미지가 들어간다. 사진 프록시 코드는 그대로 남아 있어서 키만 등록하면 코드 수정 없이 실사진으로 바뀐다.

<a id="adr-4"></a>
## ADR-4 · 초성 검색을 라이브러리 없이 직접 구현한다

### 문제 상황

목적지 자동완성 버그를 고치면서(TS-004) 초성 검색까지 같이 넣게 됐다.

### 검토한 선택지

1. `es-hangul` 같은 기존 한글 처리 라이브러리를 붙인다
2. 유니코드 완성형 음절 계산으로 직접 짠다

### 결정

2번. 필요한 것만 순수 함수로 직접 구현했다.

### 이유

필요한 기능이 초성 추출 + 매칭 하나뿐인데 라이브러리 전체를 번들에 넣는 건 과했다. 랜딩 페이지 JS 예산이 150KB라 이것도 고려 대상이었다. 완성형 한글 초성 계산 공식은 짧고 고정적이라 직접 구현 비용이 낮았다.

### 결과

번들 증가 없이 기능이 들어갔다. 완성형 음절만 처리해서 IME 조합 중간 상태는 대상 밖인데, 실사용에서 문제가 안 돼서 한계를 알면서 받아들였다.

<a id="adr-5"></a>
## ADR-5 · 소셜 로그인을 제거하고 이메일 인증으로 단일화한다

### 문제 상황

로그인 화면에 Google/Kakao/Naver 버튼이 있었는데 실제로 연동된 provider가 하나도 없었다. 아이콘도 외부 호스팅 이미지를 그대로 참조해서 스크린샷에는 흰 배경만 남았다.

### 검토한 선택지

1. provider 3개를 실제로 구현해서 완성한다
2. 미완성인 채로 "준비 중" 표시만 단다
3. 아예 없앤다

### 결정

3번. 이메일/비밀번호 단일 경로로 정리했다.

### 이유

MVP 범위에서 provider 3개를 다 붙이는 건 일정 대비 과했다. 그리고 동작하지 않는 버튼을 화면에 남겨두는 게 오히려 신뢰를 더 깎는다고 봤다.

### 결과

코드 76줄이 지워졌다. 호출자가 사라진 콜백을 정리하다가 그 안에 있던 `alert()` 1곳도 같이 없어졌다(TS-002와 연결되는 지점). 회원가입 도중 사용자 행 insert가 실패한 계정을 위한 폴백 생성 로직은 남겼다. 소셜 로그인과 무관하게 필요한 안전장치라서.

<a id="adr-6"></a>
## ADR-6 · LLM 단일 호출을 6단계 파이프라인으로 바꾸고 폴백을 없앤다

### 문제 상황

사용자 불만이 네 가지였다. 같은 장소가 여러 날 중복, 동선 무시, 늘 같은 곳만 추천, 식당이 "소문난 맛집" 같은 실체 없는 이름.

원인은 구조에 있었다. Gemini에게 "일정 전체를 짜 줘"라고 한 번 물어보고 그 텍스트를 그대로 화면에 뿌리고 있었다. 중복 금지도 동선도 실재하는 상호명도 전부 프롬프트 문장으로만 부탁하고 검증하는 코드가 없었다. 모델이 지키면 지켜지고 안 지키면 그대로 나갔다.

### 검토한 선택지

1. 프롬프트를 더 강하게 쓰고 예시를 늘린다
2. 응답을 받은 뒤 코드로 검사해서 어긋나면 재요청한다
3. 책임을 쪼개서 검증 가능한 건 코드가 맡고 모델은 코드가 못 하는 것만 맡는다

### 결정

3번. 6단계로 나눴다.

```
1. Gemini       후보 장소 이름만 제안 (필요량의 2.5배 오버샘플링)
2. Kakao Local  실재 여부 조회 → 실좌표 확보. 없으면 탈락
3. k-means      정원 제약 클러스터링으로 날짜 배정
4. TSP          하루 안 방문 순서 결정
5. 스케줄러     이동·체류 시간으로 시각 배치, 식사 삽입
6. Gemini       각 활동의 설명 문장만 작성
```

여기에 더해 실패 시 가짜 일정을 내보내던 폴백을 전부 걷어냈다.

### 이유

프롬프트를 강화하는 건 1번 방식인데, 잘 되는지 확인할 방법이 없다. 재요청 방식(2번)은 호출 횟수가 늘어나는데 무료 한도가 하루 20회라 감당이 안 된다.

불만 네 개가 각각 어디서 풀리는지가 명확했다. 중복은 3단계 클러스터링이 한 장소를 한 날에만 배정하면서, 동선은 4단계 TSP가, 반복은 1단계 오버샘플링 + 2단계 탈락으로 후보 풀이 매번 달라지면서, 가짜 식당은 식당을 모델이 아니라 카카오 주변 검색에서 가져오면서 풀린다.

폴백을 없앤 건 사용자가 가짜 일정을 진짜로 받아들이는 게 더 나쁘다고 봤기 때문이다.

### 결과

응답 시간이 16.2초에서 7.2초로 줄었다(구조 개편 전은 4건 평균, 이후는 1건 실측이라 참고치다). 중간 단계가 전부 코드라 네트워크 대기가 없다.

폴백을 지우니 숨어 있던 고장이 바로 드러났다. 무료 한도 소진이 곧바로 생성 실패로 나타났고, 그게 500으로 뭉뚱그려져 틀린 안내가 나가고 있었다(TS-030). 실패를 드러내기로 한 이상 그 실패를 어떻게 말할지는 별도 설계가 필요했고, 그래서 장소 부족 422와 한도 소진 429로 나눴다.

<a id="adr-7"></a>
## ADR-7 · 날짜 배정과 순서 결정을 결정적 알고리즘으로 짠다

### 문제 상황

6단계 파이프라인에서 3·4단계를 어떻게 구현할지 정해야 했다. 날짜별로 장소를 묶고, 하루 안에서 순서를 정하는 문제다.

### 검토한 선택지

1. 거리순으로 대충 자른다
2. 일반 k-means로 묶는다
3. 정원 제약을 건 k-means로 묶고, 하루 순서는 완전탐색으로 최단 경로를 찾는다

### 결정

3번. 클러스터 정원을 강도 설정의 상한(여유롭게 3, 빡빡하게 8)으로 두고, 하루 순서는 8곳 이하일 때 완전탐색, 넘으면 최근접 이웃으로 내려간다.

시드는 난수 대신 가장 먼 점부터 잡는 방식을 썼다.

### 이유

일반 k-means는 정원 개념이 없어서 하루에 12곳, 다른 날에 2곳이 몰릴 수 있다. 여행 일정에서는 하루에 담을 수 있는 양이 정해져 있으니 정원 제약이 필요했다.

완전탐색이 가능한 이유는 클러스터 정원이 최대 8이라서다. 8개 순열은 40,320개인데 거리 계산이 단순해서 실측상 문제가 안 된다. 근사 알고리즘을 쓸 이유가 없었다.

난수를 안 쓴 건 테스트 때문이다. 시드가 랜덤이면 같은 입력에 다른 결과가 나와서 회귀 테스트를 쓸 수가 없다.

### 결과

같은 조건이면 항상 같은 일정이 나온다. 알고리즘 관련 테스트를 픽스처로 고정할 수 있게 됐다.

정원을 넘긴 장소는 버리지 않고 leftover로 두고, 하한에 못 미치는 날을 중심에서 가까운 것부터 채우는 보정을 따로 넣었다.

<a id="adr-8"></a>
## ADR-8 · 설명 호출을 배치로 묶고 모델을 분리한다

### 문제 상황

설명 생성을 일차별로 호출하다 보니 3일 일정에 후보 추출 포함 4회를 썼다. 무료 한도가 모델·프로젝트당 하루 20회라 일정 5건이면 바닥났다(TS-030).

### 검토한 선택지

1. 유료 플랜으로 올린다
2. 설명 기능을 뺀다
3. 여행 전체 설명을 한 번에 받는다

### 결정

3번. 배치로 묶어서 건당 4회를 2회로 줄였다. 그리고 설명 모델만 `flash-lite`로 분리했다.

### 이유

유료 전환은 이 프로젝트 전제가 아니었다. 설명을 빼면 일정이 장소 목록으로만 남아서 서비스 가치가 떨어진다.

모델을 분리한 이유는 둘이다. 하나는 지연이다. 4일치를 한 번에 flash로 받으면 14초 상한을 넘겨서 전 일차가 강등됐다(실측 13,970ms). 출력 토큰이 지연을 지배하는 단계라 가벼운 모델이 유리하다. 다른 하나는 한도다. 한도가 모델별로 잡히니까 후보 추출과 설명이 서로 다른 버킷을 쓴다. 한쪽이 바닥나도 다른 쪽은 살아 있다.

이 단계는 장소·순서·시각이 이미 확정된 뒤라 글만 쓴다. 모델을 낮춰도 일정 품질은 안 바뀐다.

### 결과

한 번 호출로 3일치 설명이 4.6초에 나온다. 검증은 그대로 일차별로 해서, 어긋난 일차만 최소 문구로 내리고 나머지는 살린다.

남은 트레이드오프는 일수가 길어지면 응답도 길어진다는 점이다. 7일 이상에서 잘리면 일차별 검증이 잡아내서 일정 자체는 나오지만 설명 품질이 떨어진다.

<a id="adr-9"></a>
## ADR-9 · 설명을 인덱스가 아니라 장소 이름으로 대조한다

### 문제 상황

모델이 설명을 돌려줄 때 개수만 맞추고 순서를 바꿔서 주는 경우가 있었다. 그러면 A 장소에 B 설명이 조용히 붙는다. 이걸 막고 있던 건 프롬프트 문장 한 줄이 전부였다.

### 검토한 선택지

1. 프롬프트에 순서를 지키라고 더 강하게 쓴다
2. 응답 스키마에 장소 이름을 필수로 넣고 코드가 대조한다

### 결정

2번. 스키마에 `title`을 필수로 두고 이름으로 짝을 맞춘다. 어긋나면 그 날만 최소 설명으로 내린다.

### 이유

1번은 지켜졌는지 확인할 방법이 없다. 순서가 바뀌어도 에러가 안 나고 화면에는 그럴듯하게 나오기 때문에 조용히 틀린 정보가 나간다.

화면에 나가는 장소 이름은 어차피 카카오가 준 값을 쓴다. 모델 응답의 이름은 정렬 확인용으로만 쓰니까 대조에만 써도 손해가 없다.

### 결과

잘못 붙은 설명이 나갈 일은 없어졌다. 대신 모델이 이름을 정확히 못 옮기면 멀쩡한 응답도 최소 설명으로 강등된다. 강등이 타임아웃 때문인지 대조 실패 때문인지 구분하려고 사유를 로그에 남기게 했다.

<a id="adr-10"></a>
## ADR-10 · 지도 타일을 OpenStreetMap 공식 타일로 교체한다

### 문제 상황

2026년 11월에 배포 데모를 열어 보니 일정 지도가 전부 "API KEY REQUIRED" 회색 타일이었다(TS-034). 8월까지 키 없이 쓰던 CARTO 무료 basemap이 익명 접근을 막은 것이다. 지도는 일정 결과 화면의 핵심이라 그대로 둘 수 없었고, 이 프로젝트는 결제 없이 돌린다는 전제가 있다.

### 검토한 선택지

1. CARTO 계정을 만들고 API 키를 발급받아 그대로 쓴다
2. OpenStreetMap 공식 타일(`tile.openstreetmap.org`)로 바꾼다
3. 카카오 지도 JavaScript SDK로 갈아타고 Leaflet을 걷어낸다
4. MapLibre GL + 무료 벡터 타일 제공자(OpenFreeMap 등)로 바꾼다

### 결정

2번. 타일 URL 한 줄을 바꾸고, OSM 이용 조건대로 출처 표기를 켰다.

### 이유

1번은 또 하나의 키와 계정, 그리고 무료 플랜 한도를 관리해야 한다. 이번 사고의 원인이 "외부 무료 서비스의 조건 변경"인데 같은 종류의 의존을 하나 더 만드는 셈이다.

3번은 국내 지도 품질이 가장 좋다. 하지만 Leaflet 기반 마커·동선 코드를 전부 다시 써야 하고 JS 앱키 발급과 도메인 등록이 따른다. 하루 안에 끝내는 범위를 넘는다. 이미 장소 검증에 카카오 REST 키를 쓰고 있어서 생태계 통일이라는 장점은 있다. 나중에 지도 품질이 문제가 되면 이쪽으로 간다.

4번은 벡터 타일이라 보기 좋고 가볍지만 렌더러 교체가 필요해 3번과 같은 이유로 지금은 과하다.

2번은 키가 필요 없고 코드 변경이 가장 작다. OSM 타일 정책은 "대량·상업 사용 금지, 출처 표기 필수"라 데모 트래픽은 문제가 없다.

### 결과

지도가 복구됐다. 배포 번들에 `tile.openstreetmap.org`가 들어간 것을 확인했다.

남은 트레이드오프는 둘이다. 하나는 OSM 타일이 CARTO Voyager보다 색이 진하고 글자가 많아 마커가 덜 도드라진다는 점. 다른 하나는 사용량이 늘면 OSM 정책에 걸리므로 그때는 3번이나 키 발급형으로 옮겨야 한다는 점이다. 그 시점을 놓치지 않도록 코드 주석과 TS-034에 조건을 적어 뒀다.
