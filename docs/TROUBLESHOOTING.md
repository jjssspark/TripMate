<a id="ts-036"></a>
## TS-036 · 병렬 작업 중 커밋해 메시지와 내용이 어긋나고 원격이 빌드 불가로 푸시됨

### 현상

커밋 `483b9ac`의 메시지는 "지도 타일을 CARTO에서 OpenStreetMap으로 바꾼다"였는데 실제 내용은 `PlanResultView.tsx`를 920줄에서 563줄로 쪼갠 분리 작업 전체였다. 분리로 생긴 새 파일들은 커밋에 없었다. 그 상태로 푸시돼서 원격 HEAD는 import 대상이 없어 빌드가 안 되는 트리가 됐다.

### 원인 분석

같은 작업 트리에서 컴포넌트 분리 작업자 둘이 파일을 고치는 중이었고, 나는 그중 한 파일의 7줄짜리 타일 URL 수정만 먼저 커밋하려고 했다. `git diff --stat`으로 7줄인 걸 확인하고 수십 초 뒤 `git add`를 했는데, 그 사이에 작업자가 파일을 통째로 교체했다. 확인한 시점과 올린 시점의 파일이 달랐던 것이다.

`git show HEAD:src/components/PlanResultView.tsx | grep plan-result`가 2건 나와서 커밋된 파일이 이미 분리된 버전임을 확인했다.

### 시도한 방법

커밋 직전 `git diff --stat`로 변경량을 봤다. 7줄로 보였지만 그건 확인 시점의 값이었고, 스테이징 직후 `git diff --cached --stat`로 봤어야 했다.

### 최종 해결

이미 푸시된 뒤라 히스토리를 고치지 않았다. 다음 커밋 `f7cc0ac`에 새 파일 전부와 나머지 분리 작업을 올리고, 메시지 본문에 직전 커밋이 빌드되지 않는 이유와 이 커밋이 바로잡는다는 사실을 적었다. 깨진 커밋이 올라가 있던 동안 배포 번들을 받아 보니 이전 타일 주소가 그대로였다. Netlify가 빌드 실패 시 이전 배포를 유지해서 서비스 영향은 없었다.

### 배운 점

"방금 확인했다"는 공유 상태에서는 보장이 아니다. 여러 작업자가 동시에 고치는 동안은 커밋하지 않거나 `git worktree`로 트리를 분리해야 한다. 그리고 빌드가 깨진 커밋이 올라가도 사이트가 멀쩡해 보이는 건 배포 플랫폼이 실패를 삼켜 주기 때문이지 코드가 괜찮아서가 아니다. 푸시 뒤 배포 결과를 보는 습관이 필요하다.

<a id="ts-035"></a>
## TS-035 · lint 설정 블록에 플러그인 미등록 — `npm run lint` 전체 실행 불가

### 현상

`npx eslint .`가 파일을 하나도 검사하지 못하고 끝났다. `src server netlify` 폴더만 지정하면 멀쩡히 돌았다.

```
A configuration object specifies rule "@typescript-eslint/no-explicit-any", but could not find plugin "@typescript-eslint".
```

### 원인 분석

`eslint.config.js`가 세 블록이다. `src/**` 블록과 `server/**, netlify/**` 블록은 `tseslint.configs.recommended`를 extends해서 플러그인이 등록된다. 세 번째 `**/*.{ts,tsx}` 블록은 `no-explicit-any`를 warn으로 두는 규칙만 추가하고 플러그인 등록이 없다. `tests/` 18개 파일은 앞 두 블록 어디에도 안 들어가서 세 번째 블록만 적용되고, 플러그인 없는 블록에서 규칙을 쓰는 순간 전체가 죽는다.

`git ls-files '*.ts' '*.tsx'`에서 `src/ server/ netlify/ vite.config.ts`를 빼면 남는 게 정확히 `tests/`뿐이었다.

### 시도한 방법

`typescript-eslint` 패키지 누락을 먼저 의심했는데 설치돼 있었다. 패키지가 아니라 flat config에서 플러그인이 블록 단위로 등록된다는 특성이 원인이었다.

### 최종 해결

세 번째 블록에 `plugins: { '@typescript-eslint': tseslint.plugin }`을 등록하고, Node 블록 `files`에 `tests/**/*.ts`를 넣었다. 테스트의 목 인자 `_req`가 `no-unused-vars`에 걸려 `argsIgnorePattern: '^_'`도 추가했다. 같은 날 any 37곳을 전부 실제 타입으로 바꾼 뒤 규칙을 `error`로 올렸다.

### 배운 점

flat config에서 어떤 블록이 "규칙만" 추가하면, 그 블록만 적용되는 파일이 하나라도 생기는 순간 전체가 깨진다. lint가 CI에 없어서 두 달 넘게 깨진 채로 있었다. 다음은 GitHub Actions에 lint·typecheck·test를 붙이는 일이다.

<a id="ts-034"></a>
## TS-034 · 지도가 전부 "API KEY REQUIRED" 타일 — CARTO가 익명 접근을 막음

### 현상

배포 데모에서 새로 일정을 만들면 결과 화면의 지도가 회색 바둑판이고 타일마다 "API KEY REQUIRED / carto.com/basemaps/apikey"라고 찍혀 있었다. 번호 마커는 제 위치에 찍혔다. 처음 보고는 "무슨 API 키가 만료된 것 같다"였다.

### 원인 분석

지도 배경 타일을 `basemaps.cartocdn.com`에서 받아왔는데, CARTO가 무료 basemap의 키 없는 접근을 막았다. 코드는 8월 이후 바뀐 게 없고 외부 서비스 정책이 바뀐 것이다.

확인은 `curl`로 했다. 타일 두 장이 둘 다 HTTP 200, `image/png`인데 크기가 2,049바이트로 똑같았고, 열어 보니 지도가 아니라 안내 그림이었다. 같은 좌표의 OpenStreetMap 공식 타일은 12KB짜리 실제 지도가 왔다.

### 시도한 방법

1. 보고대로 Google Places 키 만료를 의심했다. 그런데 Places 키는 장소 사진 경로에만 쓰이고 배포 서버엔 애초에 등록돼 있지도 않았다. 지도는 Leaflet + 타일 서버라 별개다.
2. 서버 응답에 좌표가 빠졌나 봤다. 배포 API로 부산 1박 2일을 만들어 보니 12곳 전부 위경도가 있었다.
3. 타일 URL을 상태 코드만 찍어 봤더니 200이라 "정상"으로 넘길 뻔했다. 본문을 받아 열어 봐야 보이는 장애였다.

### 최종 해결

타일 레이어를 OpenStreetMap 공식 타일로 바꾸고 OSM 이용 조건에 맞춰 출처 표기를 켰다. CARTO 키 발급, 카카오 지도 SDK, MapLibre+벡터 타일도 놓고 봤고 판단 근거는 ADR-10에 적었다. 푸시 후 배포 번들에 `tile.openstreetmap.org`가 들어 있는 걸 확인했다.

### 배운 점

HTTP 200은 "요청이 처리됐다"지 "원하는 내용이 왔다"가 아니다. 외부 무료 서비스는 코드가 안 바뀌어도 어느 날 조용히 동작이 바뀐다. 의존하는 무료 자원은 언제 어떤 조건으로 쓰기 시작했는지 적어 둬야 나중에 원인을 좁힐 수 있다. OSM 공식 타일도 대량·상업 사용은 금지라 트래픽이 늘면 다시 봐야 한다.

<a id="ts-031"></a>
## TS-031 · 로컬은 되는데 배포본만 일정 생성 500

### 현상

로컬에서는 일정이 잘 나오는데 배포된 데모에서만 500이 떴다. 응답 메시지는 "일정을 만들지 못했습니다. 잠시 후 다시 시도해 주세요"였고, 4분 동안 6번 눌러도 전부 같았다. 이상했던 건 응답이 1.36초 만에 돌아온다는 점이었다. 서버 예산이 25초인데 근처도 안 갔다.

### 원인 분석

Netlify 환경변수에 `KAKAO_REST_API_KEY`가 없었다. 대시보드에는 Gemini 키와 Supabase 키 3개만 등록돼 있었다.

파이프라인 2단계가 카카오 로컬 API로 장소가 실재하는지 대조하는데, 키가 없으니 조회가 전부 실패하고 검증을 통과한 장소가 0건이 된다. 그 뒤 단계는 진행 자체가 불가능하다. 1.36초에 끝난 이유도 이거였다. Gemini 호출까지 가지도 못하고 그 앞에서 죽은 것.

전날 커밋에서 파이프라인을 교체하면서 카카오 실재 검증을 새로 넣었다. 그전에는 Gemini 응답을 그대로 썼으니 카카오 키 없이도 돌아갔다. 새 필수 의존성이 생겼는데 배포 환경에만 반영을 안 한 상태였다.

### 시도한 방법

1. Gemini 키 이름이 안 맞는 걸 의심했다. 대시보드에는 `VITE_GEMINI_API_KEY`로 돼 있어서 코드가 `GEMINI_API_KEY`만 읽으면 이게 원인일 거라고 봤는데, 코드가 두 이름을 다 읽고 있었다. 애초에 Gemini 단계까지 가지도 못하는 상황이었다.
2. Netlify 함수 타임아웃(10초)을 의심했다. 서버 예산 25초가 상한을 넘겨 잘리는 줄 알았는데, 응답이 1.36초에 오니까 말이 안 됐다. 타임아웃이면 10초를 채우고 죽어야 한다.
3. 에러 메시지를 믿고 재시도했다. "잠시 후 다시 시도"라길래 4분간 6번 폴링했는데 전부 같은 실패였다.

### 최종 해결

Netlify 대시보드에 `KAKAO_REST_API_KEY`를 Functions scope로 등록하고 재배포했다. 실제 요청을 넣어보니 11.9초에 200이 오고, 실제 상호명이 들어간 일정이 나왔다.

README 환경변수 표에도 이 키가 빠져 있어서 같이 채웠다. `.env.example`에는 있는데 문서에만 없어서, 문서만 보고 배포하면 무조건 같은 사고가 난다.

### 배운 점

에러 메시지가 원인을 가릴 수 있다. "잠시 후 다시 시도"는 일시적 장애를 뜻하는데 실제로는 키를 넣기 전엔 영원히 안 풀리는 상태였다.

그리고 응답 시간 자체가 진단 정보다. 예산 25초짜리가 1.36초에 실패했으면 느린 단계에 도달조차 못 했다는 뜻이다. 이 숫자 하나가 첫 가설을 반증하고 있었는데 처음엔 그냥 넘겼다.

타입 체크도 테스트도 전부 통과한 상태에서 운영만 하루 넘게 죽어 있었다. 로컬과 운영의 환경변수 차이는 코드가 아무리 정확해도 안 잡아준다.

<a id="ts-030"></a>
## TS-030 · 무료 한도를 건당 4회씩 써서 소진, 429를 500으로 뭉뚱그림

### 현상

일정 만들기를 누르면 "조건을 조금 바꿔 다시 시도해 주세요"가 뜬다. 조건을 아무리 바꿔도 계속 실패한다.

### 원인 분석

Gemini 무료 티어의 429였는데, 원인이 세 겹이었다.

호출량이 먼저다. 파이프라인 1회가 후보 추출 1회 + 일수만큼의 설명 호출을 썼다. 3일 일정이면 4회. 무료 한도가 모델·프로젝트당 하루 20회라 일정 5건이면 바닥난다.

두 번째는 오분류다. 429가 500 `PLAN_GENERATION_FAILED`로 뭉뚱그려져 있었다. 사용자한테 조건을 바꾸라고 안내하는데 조건을 바꿔도 절대 안 풀린다. 할 수 있는 건 기다리는 것뿐인데 그 말을 안 해줬다.

세 번째는 재시도가 상황을 악화시킨 것. 타임아웃이 아닌 오류는 즉시 한 번 더 호출하게 돼 있었는데, 429는 19초 뒤에 재시도하라고 알려준다. 바로 다시 부르니 똑같이 실패하면서 남은 한도만 한 번 더 깎았다.

계측해보니 후보 추출은 통과하고 설명 단계에서 429가 나고 있었다. 설명에서 나면 폴백 문구로라도 일정이 나오는데, 후보 추출에서 나면 전체가 실패한다. 사용자가 본 건 후자였다.

배경도 하나 있다. 전날 커밋에서 실패 시 가짜 일정을 내보내던 폴백을 지웠다. 예전엔 가짜라도 나오던 자리가 그대로 에러로 드러난 것이라, 버그라기보다 설계대로 동작한 결과였다.

### 시도한 방법

| 시도 | 결과 |
|---|---|
| `.env` 키 이름 불일치 의심 | 원인 아님. 코드가 두 이름을 다 읽고 있었다 |
| `gemini-2.0-flash`로 모델 우회 | 404. 폐기된 모델이었다 |
| 공식 문서에서 한도 수치 확인 | 문서가 수치를 안 알려준다. 429 응답 본문이 유일한 근거였다 |

### 최종 해결

무료 티어를 유지하는 전제로 세 가지를 고쳤다.

설명 호출을 배치로 합쳤다. 일차별로 부르던 걸 여행 전체 한 번으로 바꿔서 3일 기준 4회가 2회가 됐다. 검증은 그대로 일차별로 해서, 어긋난 일차만 폴백 문구로 내리고 나머지는 살린다.

429 전용 에러를 만들었다. 세 진입점에서 `AI_QUOTA_EXCEEDED` + 429로 응답한다. 재시도 가능 시각도 같이 준다. 무료 한도는 태평양시 자정에 리셋되는데 서머타임 때문에 한국시간으로는 16시와 17시 사이를 왔다갔다한다. 하드코딩하면 1년의 절반은 틀린 안내가 나가서, 다음 자정을 계산해 한국시간으로 환산했다.

재시도 대상에서 타임아웃과 쿼터를 뺐다. 일시적 API 오류만 한 번 더 시도한다.

검증은 실제 HTTP 호출로 했다. 한도가 소진된 상태에서 0.55초 만에 429가 떨어지고, 25초 예산을 태우지 않는다.

### 배운 점

폴백을 지우면 고장이 드러난다. 그런데 드러난 고장을 사용자한테 어떻게 말할지는 별도 설계가 필요하다. 500은 "우리 잘못이니 곧 고치겠다"는 뜻이고 429는 "당신 잘못이 아니니 기다리면 된다"는 뜻인데, 둘을 한 메시지로 합치면 사용자는 아무것도 할 수 없다.

무료 한도 문제는 한도를 늘리는 것보다 소비량을 줄이는 게 먼저다. 호출 4회를 2회로 만든 건 코드 한 군데였다.

<a id="ts-029"></a>
## TS-029 · 429를 분당 한도로 오판해 70초를 기다림

### 현상

라이브 검증 중에 수정 요청이 429로 실패했다. 70초 기다렸다가 다시 눌렀는데 똑같이 429였다.

### 원인 분석

처음엔 분당 5회 제한이라고 보고 대기 후 재시도로 대응했다. 그런데 429 응답 본문의 위반 필드를 읽어보니 `GenerateRequestsPerDayPerProjectPerModel-FreeTier (limit: 20/day)`였다.

분당 한도와 일일 한도가 둘 다 있는데 걸린 건 후자였다. 일일 한도는 기다린다고 풀리는 게 아니다.

계산해보니 파이프라인 1회가 후보 추출 1회 + 일수만큼의 설명이라, 2박3일이면 4회, 14일이면 15회를 쓴다. 하루 검증 예산이 생각보다 훨씬 빨리 소진되는 구조였다.

### 시도한 방법

70초 대기 후 재시도. 당연히 같은 429였다. 일일 한도에는 대기가 아무 의미가 없다.

### 최종 해결

이건 근본 해결이 아니라 우회다. 라이브 재검증을 포기하고, 실제 실패 경로를 그대로 재현하는 단위 테스트로 검증 근거를 대체했다. 소비량 자체를 줄이는 근본 해결은 이틀 뒤 TS-030에서 했다.

### 배운 점

레이트 리밋은 종류를 확인하기 전에 기다리지 않는다. 429 본문의 `quotaId`가 어느 한도인지 다 말해준다. 대기 70초는 그 한 줄을 안 읽어서 쓴 비용이었다.

<a id="ts-028"></a>
## TS-028 · 제외 지시가 식당 선택에 닿는 코드 경로가 아예 없었음

### 현상

일정을 만든 뒤 "가는 장소는 바꿔줘"로 수정 요청을 넣었다. 관광지는 대부분 바뀌었는데 식당 한 곳이 원본과 수정본 양쪽에 그대로 남았다. 에러는 없었다.

### 원인 분석

제외 지시가 자유 텍스트 `comments`에만 들어가고 있었다. `comments`는 후보 추출 LLM 프롬프트로만 흘러간다.

그런데 식당과 카페는 후보 LLM이 뽑지 않는다. `pickMeals`가 카카오 검색으로 직접 가져온다. 즉 제외 문구가 식사 선택에 닿을 수 있는 코드 경로 자체가 없었다. 확률 문제가 아니라 구조적인 구멍이었다.

### 시도한 방법

처음엔 "LLM이 프롬프트 지시를 가끔 무시하는 알려진 한계"로 진단했다. 이걸 받아들였으면 프롬프트 문구를 강화하는 데 시간을 썼을 거고 효과는 0이었다.

방향을 바꾼 근거는 재등장한 대상이 식당이라는 점이었다. 식당은 LLM을 거치지 않으니까 "LLM이 무시했다"로는 설명이 안 된다. 그래서 `pickMeals` 호출부를 따라가 보니 제외 목록이 도달하지 않는 게 코드로 확인됐다.

### 최종 해결

제외를 프롬프트가 아니라 코드가 강제하게 바꿨다. 요청 타입에 `excludeNames`를 넣고, 정규화한 집합을 장소 해석 결과 · 식사 선택 · 관광지 보충 경로 세 군데에 전부 적용했다. 사용자가 이름으로 찍은 필수 방문지는 제외보다 우선한다.

검증은 수정 전 코드로 되돌려서 테스트 2건이 먼저 실패하는 걸 확인하고 시작했다. 그중 하나가 실제 라이브 실패 경로를 그대로 재현한다.

### 배운 점

검증할 수 있는 제약을 프롬프트에만 두면 그건 제약이 아니다.

그리고 "LLM이 원래 그렇다"는 진단은 그 값이 정말 LLM에서 오는지 확인한 뒤에만 쓸 수 있다. 값의 출처부터 따졌으면 진단이 한 번에 끝났을 문제였다.

<a id="ts-027"></a>
## TS-027 · 「산장」이 「산」에 걸려 숙박 시설이 자연으로 분류

### 현상

카카오 API가 돌려준 `category_name: "여행 > 숙박 > 산장,별장"`이 자연 카테고리로 들어갔다. 에러는 없다.

카테고리가 체류 시간을 결정한다. 자연 120분, 맛집 60분. 잘못 분류된 장소 하나가 그날 이후 일정 전체를 60분씩 밀어낸다.

### 원인 분석

자연 토큰(산, 오름, 해변, 폭포 …) 부분 문자열 검사를 카테고리 코드 매핑보다 먼저 실행하고 있었다. "산장"이 "산"에 걸린다.

근본은 확정 정보(카테고리 코드)와 추정 정보(이름에 든 단어)를 같은 우선순위로 취급한 것이다.

### 시도한 방법

이름 기반 자연 분류를 아예 빼려고 했는데 기각했다. 실제 API 응답을 조회해보니 성산일출봉은 카테고리 코드가 빈 문자열로 오고, 관광명소 코드(`AT4`)에는 해수욕장과 전망대가 섞여 들어온다. 코드만으로는 자연과 인공을 나눌 수 없었다.

### 최종 해결

확정 코드를 먼저 적용하고, 코드가 자연/관광을 못 가르는 구간에서만 이름으로 재분류하게 순서를 뒤집었다. 테스트에 숙박·산장 케이스를 픽스처로 남겼다.

### 배운 점

에러가 안 나는 버그다. 잘못된 값이 조용히 다음 계층의 입력이 돼서 전혀 다른 증상(시간이 밀림)으로 나타난다.

분류 함수를 쓸 땐 확정 정보와 추정 정보의 우선순위를 코드에 명시적으로 갈라놔야 한다.

## TS-026 · 상한에서 역산해 예산을 나눴다가 후보 추출 4회 중 3회 실패

### 현상

일정 생성이 계속 실패했다. "후보 추출 시간이 초과되었습니다." 로직은 안 건드리고 타임아웃 상수만 조정한 직후였다.

### 원인 분석

재시도 예산 5초가 실제 응답 시간보다 짧았다. 실측이 6.1초, 10.4초였다.

총 30초 상한에 맞추려고 8 + 5 + 10 = 23초로 역산했는데, 그 계산이 "재시도 자리는 반드시 필요하다"는 검증 안 된 전제 위에 있었다. 실제로는 1차 시도가 타임아웃으로 끝났으면 재시도는 거의 무의미하다. 느린 요청은 다시 해도 느리다. 쓸모없는 재시도 몫을 남겨두느라 1차 예산과 재시도 예산이 둘 다 작아진 상태였다.

관측된 지연 분포를 안 보고 상한만 보고 상수를 정한 게 진짜 원인이다. TS-012와 같은 계열의 재발인데, 그때는 목업으로 조용히 강등됐고 이번엔 명시적으로 실패했다.

### 시도한 방법

| 시도 | 결과 |
|---|---|
| 1차 예산만 8초 → 10초 | 재시도 몫을 그대로 두니 총 30초를 넘긴다 |
| 재시도 자체를 제거 | 기각. 일시적 5xx나 네트워크 오류까지 같이 죽는다 |

### 최종 해결

타임아웃과 일시적 오류를 구분했다. 타임아웃은 재시도 없이 바로 던지고, 그 외 오류만 짧은 예산으로 재시도한다. 재시도가 사실상 안 일어나게 되면서 1차 예산을 14초까지 확보했다.

후보 추출 3회 연속 성공, 전체 파이프라인 12초로 확인했다.

### 배운 점

상한에서 역산해 예산을 나누기 전에 각 구간의 실제 지연부터 재야 한다.

그리고 재시도를 예산에 넣기 전에 "이 실패가 재시도로 나아지는 종류인가"부터 따져야 한다. 타임아웃 재시도는 대부분 예산만 먹고 성공률은 안 올린다.

<a id="ts-025"></a>
## TS-025 · 정규식 `\W`가 한글을 다 지워 모든 장소가 같은 키가 될 뻔함

### 현상

중복 제거에 쓰려던 이름 정규화 함수가 한글 입력을 빈 문자열로 만들었다. 에러는 안 난다.

```
"성산일출봉".replace(/[\s\W_]/gu, "")  →  ''
"Seongsan".replace(/[\s\W_]/gu, "")    →  'Seongsan'
```

이대로 나갔으면 모든 한국 장소가 같은 키(빈 문자열)로 묶여서 하루에 장소가 1곳만 남는다. 이번 작업의 출발점이 "같은 장소가 여러 날 반복된다"였는데 정반대 극단으로 무너지는 형태였다.

### 원인 분석

`\W`는 `[^A-Za-z0-9_]`라는 ASCII 기준 정의다. `u` 플래그를 붙여도 이 정의는 유니코드로 확장되지 않는다. `u`는 서로게이트 페어 처리랑 `\p{...}` 사용을 열어줄 뿐이다. 한글은 전부 "단어 문자가 아닌 것"으로 판정돼 지워진다.

계획 문서에 적혀 있던 코드를 그대로 옮긴 거였고, 실제 입력값으로 돌려본 적이 없었다.

### 시도한 방법

제거할 문자를 직접 열거하는 방식(`/[\s\-_.!?',]/g`)으로 바꿨다. 한글은 살아남았지만 괄호가 남아서 "우진해장국(본점)"과 "우진해장국 본점"이 서로 다른 장소로 갈렸다. 카카오 응답에 괄호 표기가 실제로 섞여 온다.

### 최종 해결

제거 대상을 열거하는 대신 남길 대상을 지정했다.

```ts
name.replace(/[^\p{L}\p{N}]/gu, "").toLowerCase()
```

모든 언어의 문자와 숫자만 남기니까 공백·구두점·괄호는 다 흡수되고 한글은 보존된다. 실제 파이프라인에서 제주도 2박3일 활동 21개, 중복 0건을 확인했다.

### 배운 점

한국어 서비스에서 `\w` `\W` `\b`는 기본적으로 의심 대상이다. ASCII 기준이고 `u` 플래그로도 안 바뀐다.

그리고 계획서에 코드가 적혀 있다는 게 그 코드가 검증됐다는 뜻은 아니다. 옮겨 적기 전에 실제 값으로 한 번 돌려본다.

<a id="ts-012"></a>
## TS-012 · 타임아웃 예산 배분 오류로 가짜 일정이 조용히 나감

### 현상

AI가 만든 일정의 장소 이름이 전부 "제주도 인기 명소 3" 같은 일반명사로 나왔다. 사용자 입장에선 그냥 AI 추천 품질이 나쁜 걸로 보인다.

### 원인 분석

"로딩 30초 이내" 요구에 맞춰 27초 예산을 도입하면서 배분을 잘못했다. 주 모델에 18초만 주고 재시도에 5.5초를 남겼는데, 재시도는 빠른 실패에만 의미가 있어서 타임아웃으로 실패하면 남은 예산으로 아무것도 못 한다.

결국 예외가 나면서 기존 폴백(목업 일정)이 반환됐는데, 그 폴백이 정상 응답과 구분이 안 된 채 그대로 화면에 나갔다. Gemini 응답 시간이 17~25초 사이로 흔들려서 임계값을 간헐적으로 넘나든 것도 확인의 실마리였다.

### 시도한 방법

처음엔 프롬프트가 부실해서 품질이 낮다고 보고 프롬프트 규칙을 강화했다. 증상은 그대로였다. Gemini가 애초에 호출되지 못하고 있었으니 프롬프트를 아무리 고쳐도 닿지 않는 지점이었다.

### 최종 해결

당시에는 주 모델에 예산을 몰아주고, 폴백이 나갈 때 `isFallback: true`를 응답에 실어 화면에 드러나게 하는 선에서 끝냈다. 근본 해결은 아니었고 그렇게 기록해뒀다.

이후 파이프라인을 교체하면서 판단을 뒤집었다. 당시엔 "폴백이 나가는 걸 표시하자"였는데, 지금은 "실재하지 않는 일정을 그럴듯하게 보여주느니 실패를 드러내자"로 바꿨다. 대신 실패를 원인별로 나눈다. 장소 부족은 422, AI 한도 소진은 429다.

폴백이 사라지자 숨어 있던 문제가 바로 드러났다. 그게 TS-030이다.

### 배운 점

타임아웃은 "얼마 안에 끝낼까"만큼 "그 예산을 어떻게 나눌까"가 중요하다.

조용한 폴백은 버그를 품질 문제로 위장한다. 폴백이 나갔으면 폴백이라는 게 드러나야 원인 조사가 엉뚱한 데서 시작되지 않는다.

<a id="ts-004"></a>
## TS-004 · 자동완성이 정확히 다 입력한 순간 후보를 감춤

### 현상

목적지 입력란에 "도쿄"를 끝까지 치면 목록에 분명 있는데도 자동완성에서 사라졌다. 한 글자 지우면 다시 보였다. "도"에서는 보이고 "도쿄"가 되는 순간 사라지는 패턴이었다.

### 원인 분석

필터 조건에 입력값과 완전히 같은 후보를 제외하는 절이 있었다. "이미 입력한 걸 또 제안하지 말자"는 의도였겠지만, 정작 사용자가 지명을 정확히 아는 가장 흔한 경우에 목록이 통째로 비어버린다.

### 시도한 방법

데이터가 빠졌나 싶어 목록부터 확인했는데 "도쿄"는 멀쩡히 있었다. 데이터가 아니라 조회 조건 문제라는 게 이 시점에 확정됐다.

### 최종 해결

검색 로직을 컴포넌트 밖 순수 함수로 빼고, 완전일치를 배제하는 대신 맨 위로 올리는 랭킹 방식으로 바꿨다. 완전일치 → 접두 → 포함 → 초성 순이다. 겸사겸사 초성 검색도 넣었다.

### 배운 점

중복 제거처럼 보이는 방어 조건이 정상 경로를 막는 경우가 있다. 필터에 배제 조건을 넣을 땐 "이 조건이 참이 되는 상황이 정말 예외적인가"를 먼저 따져야 한다.

"목록에 있는데 안 나온다"는 데이터가 아니라 조회 조건을 의심하라는 신호다.

<a id="ts-003"></a>
## TS-003 · Supabase 자동 일시정지로 전 기능 Failed to fetch

### 현상

로컬 dev 서버는 정상인데 브라우저에서 로그인·일정 저장 등 Supabase가 끼는 동작이 전부 실패했다. 화면엔 `Failed to fetch`만 뜨고, dev 서버 로그에는 요청 흔적조차 없었다.

### 원인 분석

Supabase 무료 플랜 프로젝트가 비활성 기간이 쌓여 자동 일시정지되면서 프로젝트 도메인이 DNS에서 사라졌다. 브라우저는 DNS 해석 단계에서 죽으니까 HTTP 상태 코드조차 못 받는다.

이 앱은 Supabase를 브라우저에서 직접 호출하는 구조라 로컬 Express 서버 로그에는 애초에 남을 이유가 없었다.

### 시도한 방법

1. dev 서버 로그를 뒤졌다. 단서 0건. 서버를 안 거치는 구조라 당연했다.
2. 그날 건드린 코드 커밋을 의심했다. 무관으로 판명.
3. `curl`로 확인했을 때 `HTTP=000`이 나왔는데, 이때 내 실행 환경 네트워크부터 배제했어야 했다. 그걸 안 해서 진단이 한 바퀴 더 돌았다.

### 최종 해결

Supabase 대시보드에서 프로젝트를 Resume 했다. 다만 바로 복구되지 않고 인증 → REST 순으로 2분에 걸쳐 단계적으로 올라온다는 걸 실측으로 확인했다. 복구 중간에 `PGRST002`나 404가 떠서 테이블이 지워진 걸로 오해하기 쉬운데 그냥 기동 중인 상태다.

### 배운 점

`Failed to fetch`는 애플리케이션 에러가 아니라 네트워크 계층에서 죽었다는 신호다. `nslookup` 한 번이 서버 코드 뒤지는 30분을 아낀다.

어느 계층이 호출하는지 알아야 어느 로그를 볼지가 정해진다. 이 앱은 서버를 안 거치는 구조인데 그걸 모르면 계속 헤맨다.

<a id="ts-002"></a>
## TS-002 · `alert()`가 렌더러를 막아 브라우저 자동화가 전면 정지

### 현상

브라우저 자동화로 폼 검증을 확인하다가 클릭 이후 탭이 완전히 응답 불능이 됐다. 클릭·스크린샷·스크립트 주입이 전부 타임아웃 나고 서버 로그에는 요청이 하나도 안 찍혔다.

### 원인 분석

검증 실패를 브라우저 모달 `alert()`로 띄우고 있었다. `alert()`는 JS 실행과 렌더러를 동기적으로 막기 때문에 자동화가 보낸 후속 명령이 전부 큐에 쌓인 채 타임아웃된다. 프리즈가 아니라 모달 대기 상태였다.

### 시도한 방법

네트워크와 서버부터 봤는데 요청 자체가 안 나가고 있었다. 원인을 찾은 뒤에도 한 번 더 틀렸다. 처음엔 `alert()`이 3곳이라고 봤는데 실제로는 `src/` 전체에 10곳이었다. grep 범위를 파일 2개로 좁혔던 게 원인이었다.

디렉터리 전체로 다시 훑고도 1곳을 또 놓쳤다. 회원가입 성공 `alert()`이 남아 있었는데, 자동화가 로그인 화면까지만 가고 회원가입 완료 경로를 안 밟아서 재현이 안 됐다.

### 최종 해결

이미 있던 Toast 컴포넌트로 교체했다. 새로 만들지 않았다. 마지막 1곳까지 잡고 `src/` 전체에 `alert()` 호출이 0건인 걸 확인했다.

삭제 확인용 `confirm()`은 안전장치라 남겨뒀다. 바꾸려면 별도 확인 모달이 필요하다.

### 배운 점

`alert()`와 `confirm()`은 UX 이전에 테스트 가능성 문제다. 렌더러를 막는데 죽는 방식이 타임아웃이라 원인이 프론트에 있다는 힌트조차 안 준다. 자동화가 이유 없이 멈추면 네트워크보다 모달 API부터 grep하는 게 빠르다.

전수 조사를 두 번 실패했는데, 처음엔 코드 범위를 좁게 잡았고 두 번째는 실행 경로를 좁게 잡았다. 전수 조사의 기준은 범위만이 아니라 경로이기도 하다.

<a id="ts-001"></a>
## TS-001 · `publicDir` 미갱신으로 PWA 아이콘이 통째로 누락

### 현상

`npm run build`가 경고 하나 없이 성공했다. 그런데 배포된 앱에 PWA 설치 아이콘과 파비콘이 안 나왔다. `dist/`를 열어보니 이미지 파일이 하나도 없었다.

### 원인 분석

직전 리팩터링에서 `static/` 폴더를 `public/static/`으로 옮겼는데, `vite.config.ts`의 `publicDir: 'static'`은 그대로 뒀다. Vite는 `publicDir` 경로가 없으면 에러도 경고도 없이 조용히 건너뛴다. "빌드 성공"이 아무것도 보장해주지 못하는 상태였다.

### 시도한 방법

매니페스트 경로랑 아이콘 파일명부터 확인했는데 다 맞았다. 소스에는 있는데 산출물에만 없다는 게 확인되면서 복사 단계를 의심하게 됐고, 거기서 설정을 봤다.

### 최종 해결

`publicDir`를 실제 폴더로 고치고, 자산을 매니페스트가 참조하는 경로에 맞춰 평탄화했다. `netlify.toml`에 남아 있던 같은 종류의 죽은 리다이렉트 참조도 같이 지웠다.

### 배운 점

"빌드 성공"과 "산출물이 올바르다"는 다른 말이다.

경로가 없으면 조용히 넘어가는 설정은 실패를 신호로 안 바꿔준다. 그래서 파일을 옮기는 리팩터링에서는 옮긴 파일이 아니라 그 경로를 문자열로 알고 있던 곳을 기준으로 훑어야 한다.
