# 성능 · 품질 지표

실측 수치입니다. 측정 환경과 한계를 먼저 밝힙니다 — 숫자만 보고 그대로 인용하면 오해가 생길 수 있는 지점들이 있습니다.

## 측정 환경

- 프로덕션 빌드(`npm run build`)를 로컬에서 `node dist/server.cjs`로 직접 실행해 측정했습니다. 실제 배포된 Netlify URL이 아니라 로컬 환경입니다.
- Lighthouse는 샌드박스 컨테이너 안에서 headless Chrome으로 실행했습니다. 일반 개발 머신이나 실제 사용자 기기보다 CPU 자원이 제한적일 수 있어, 특히 모바일 쓰로틀링 수치는 실제보다 나쁘게 나올 가능성이 있습니다. 아래에 데스크톱/모바일 두 프리셋을 함께 남기고 이 차이를 그대로 기록합니다.
- 측정 시각: 2026-08-03. Gemini 응답 시간은 그날그날 API 상태에 따라 달라질 수 있습니다.
- 최종 포트폴리오용 수치는 실제 배포 URL과 일반 개발 머신(또는 실기기)에서 재측정하는 것을 권장합니다.

## 번들 크기

`npm run build` 결과입니다.

| 파일 | 원본 크기 | gzip | 예산(web 규약) | 판정 |
|---|---|---|---|---|
| `app-*.js` (React 앱 본체) | 707.94 kB | 210.09 kB | App page < 300kB | 통과 |
| `app-*.css` | 73.92 kB | 11.91 kB | App page < 50kB | 초과 |
| `landing.html` | 24.88 kB | 5.81 kB | Landing < 150kB | 통과 (React 미포함이라 여유 큼) |

CSS gzip이 예산(50kB)을 넘습니다. Tailwind 4를 쓰면서 유틸리티 클래스가 누적된 결과로 보이며, 사용하지 않는 클래스 정리나 `@layer` 범위 축소가 다음 최적화 후보입니다.

JS 번들은 트러블슈팅 문서에 기록된 과거 수치(2026-08-01, gzip 164.39 kB)보다 커졌습니다. 그 사이 늘어난 기능(자동완성 초성 검색, 지도 연동 등)을 감안해도 증가 추세는 `docs/ARCHITECTURE.md`의 "번들 크기" 개선 과제와 일치합니다 — Leaflet과 motion을 동적 import로 분리하는 작업이 아직 안 된 상태입니다.

| 지표 | 측정값 | 목표(web 규약) | 판정 |
|---|---|---|---|
| FCP | 2.8s | < 1.5s | 초과 |

모바일 프리셋(4x CPU 쓰로틀링 + 저속 4G 시뮬레이션)에서는 LCP가 27.6초까지 나왔습니다. 이 수치는 신뢰하지 않습니다 — 데스크톱 프리셋과의 격차가 비정상적으로 커서, 샌드박스 환경의 CPU 제약이 쓰로틀링과 중첩되며 과장됐을 가능성이 높습니다. 실기기나 일반 환경에서 모바일 수치를 다시 재는 것을 다음 작업으로 남겨둡니다.

데스크톱 기준으로도 LCP가 목표를 넘습니다 — 707kB 번들이 파싱·실행되는 시간이 주요 원인으로 보이며, 위 번들 크기 절의 개선 과제와 같은 뿌리입니다.

## AI 일정 생성 응답 시간

로컬 프로덕션 서버에 목적지 4곳으로 실제 `/api/generate-plan` 요청을 보내 측정했습니다(2026-08-03, Gemini `gemini-2.5-flash` 주 모델, 전부 정상 응답 — 폴백 미발동).

| 목적지 | 응답 시간 |
|---|---|
| 제주도 | 19.5s |
| 부산 | 15.4s |
| 강릉 | 17.9s |
| 전주 | 12.0s |

범위 12.0 ~ 19.5초, 평균 약 16.2초. `docs/adr-top5.md`(ADR-2)에서 정한 27초 타임아웃 예산과 30초 클라이언트 타임아웃 안에 전부 들어옵니다. 트러블슈팅 문서에 기록된 과거 관측치(17~25초 변동)와 겹치는 범위이며, 이번 4건은 그 안에서도 상대적으로 양호한 쪽에 속합니다 — 표본이 4개뿐이라 이 결과만으로 "느려졌다/빨라졌다"를 단정하기는 이릅니다.
